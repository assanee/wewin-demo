### `packages/core` ต้อง compile ไม่ใช่ share source

ผู้ตรวจสอบทดสอบบน Node 24.14 ของเครื่องนี้จริง ไม่ได้เดา: การ share TS source ทำงานได้ (pnpm symlink + realpath ทำให้ Node ยอม) **แต่**บังคับให้ทุก relative import ต้องมี `.ts` ต่อท้าย ซึ่งบังคับ `allowImportingTsExtensions` ซึ่งบังคับ `noEmit` ตลอดกาล

compile ด้วย `tsc` ธรรมดา (ไม่ bundle) แลกมาด้วย: Turbo แคชได้ · `nest build` ไม่ต้องตั้งค่าอะไร · Next RSC ได้ JS ธรรมดาไม่ต้อง `transpilePackages` · และ **สิ่งที่ CI type-check คือสิ่งเดียวกับที่ production รัน**

ผลข้างเคียงที่ต้องรู้: relative import ~20 จุดในโค้ดปัจจุบันเป็นแบบไม่มีนามสกุล (`'./pricing'`) ต้องเติม `.js` ทั้งหมด — เป็น find/replace ไม่ใช่ refactor และ vitest/Next/Vite ต่างก็ map `.js` → `.ts` ให้อยู่แล้ว

### export map: root เป็น type อย่างเดียว

ทุก runtime value ต้อง import จาก subpath (`@wewin/core/pricing`, `/validation`, …) เหตุผลเชิงรูปธรรม: **8 ไฟล์คอมโพเนนต์ปัจจุบัน import แค่ type จาก `types/catalog`** — root ที่เป็น type ล้วนจะ erase หายไปเลย ไม่ลาก barrel เข้า RSC graph และ `@wewin/core/fixtures` (ตาราง 81 สินค้า 568 บรรทัด) แบนออกจาก app code ด้วย lint rule ได้

จุดที่ต้องแก้ตอนย้าย: `shareLink.ts` import `MIN_QTY`/`MAX_QTY` จาก `quoteReducer.ts` ทำให้ `/share` ลาก `/quote` ตามมา — ย้ายสองค่านี้ไป `constants.ts`

### สิ่งที่เจอจริงตอนทำเฟส 0

- ✅ **root ที่เป็น type ล้วนบังคับได้จริงตอนรัน** ไม่ใช่แค่ข้อตกลง — `import '@wewin/core'` โยน `ERR_PACKAGE_PATH_NOT_EXPORTED` เพราะ export map ให้เฉพาะเงื่อนไข `types` ไม่มีคู่ runtime
- ✅ **`types: ["node"]` ไม่ใช่ `lib: ["DOM"]`** — `shareLink` ต้องใช้ `URLSearchParams` ซึ่งเป็นมาตรฐานเว็บที่ทั้งสอง runtime มี แต่ `lib: DOM` จะพา `window`/`document` เข้ามาด้วย และลดความบริสุทธิ์ของ core จากสิ่งที่**เครื่องมือรับประกัน** กลับไปเป็นสิ่งที่**รีวิวรับประกัน**
- ✅ ยืนยันด้วยการ grep ว่าชั้นโดเมนไม่แตะ browser API เลยสักจุด — `window` ทุกตัวที่เจอเป็น **string literal `'window'`** ที่ใช้เป็น size key ในตารางสินค้า
- 🐛 **กับดักที่ `tsc`, vitest และ `vite build` ผ่านหมด แต่ `vite dev` พัง** — `tsconfig.json` ที่ root ยัง `references` ไปหา `tsconfig.app.json` ที่ย้ายเข้า `apps/web/` ไปแล้ว · oxc ของ Vite เดินขึ้นไปหา tsconfig ให้ไฟล์ใน `packages/core/dist/` แล้วเจอ reference ที่ชี้ไฟล์ไม่มีอยู่ → **500 ทุกโมดูลของ core และ `#root` ว่างเปล่าโดยไม่มี error ใน console**
  → เจอเพราะเปิดเบราว์เซอร์จริง ไม่ใช่เพราะ CI · **เกณฑ์ผ่านของทุกเฟสต่อจากนี้ต้องรวม "เปิดหน้าเว็บจริง" ด้วย** ไม่ใช่แค่ 4 คำสั่ง

## 4. เงินและหน่วยวัด — ส่วนที่อันตรายที่สุด

ทุกด้านที่ตรวจสอบชี้กลับมาที่นี่หมด `Math.round(unitPrice * qty)` ใน `pricing.ts:130` คือการฝัง "บาทจำนวนเต็ม" ไว้ในชั้น domain

### 4.1 ความยาว — canonical ต้องละเอียดกว่ามิลลิเมตร

ร่างแรกบอก "มิลลิเมตรจำนวนเต็ม" **ยังไม่พอ** ผมยืนยันเองแล้ว:

```
gcd(5.0 mm, 1/8 นิ้ว) = gcd(5000 µm, 3175 µm) = 25 µm
```

ค่า `min`/`max`/`default` ในตาราง size profile **48 จาก 48 ค่าไม่อยู่บน grid นิ้ว** (และ 0 จาก 48 หลุด grid 5 mm) แปลว่าถ้าใช้ mm เป็น canonical แล้ว snap ตาม grid ของหน่วยที่กำลังแสดงอยู่ — **แค่สลับหน่วยแสดงผลแล้วคลิกออกจากช่อง ขนาดจริงจะเปลี่ยน** 3,200,000 µm → 3,200,400 µm

**ทางแก้:** canonical เป็น **ไมโครเมตรจำนวนเต็ม** และที่สำคัญกว่านั้น —

> **การสลับหน่วยเป็นเรื่องการแสดงผลล้วนๆ ห้าม snap ใหม่** `snapUp` ทำงานเฉพาะตอนพิมพ์ค่าใหม่ ในหน่วยที่พิมพ์ และเก็บ `entered_unit` ไว้กับบรรทัดนั้น

`EPSILON` กับ `toFixed(decimals)` ใน `validation.ts` ถูกลบทิ้ง ไม่ใช่ย้ายตามไป — มันมีอยู่เพื่อแก้ float dust ที่จะไม่มีอีกแล้วเมื่อเป็นจำนวนเต็ม

### 4.2 สกุลเงิน — ราคาฐานสกุลเดียว + อัตราที่ตรึงไว้

> **ตัดสินแล้ว** ราคาฐานเป็น **THB สกุลเดียวต่อสินค้า** แล้วแปลงตามสกุลที่ลูกค้าตั้งค่า

ร่างที่ 2 เคยแนะนำ price list ต่อสกุล — **เปลี่ยนแล้ว** เหตุผลที่เปลี่ยน: price list คือคำตอบที่ถูกในตำรา
แต่ไม่ได้ชั่งว่าใครจะดูแลมัน บริษัทที่ยังไม่ได้เผยแพร่แม้แต่สเปกโปรไฟล์ของตัวเองจะไม่มีคนมาอัปเดตราคา
9 ชุดทุกครั้งที่อะลูมิเนียมขยับ และ **price list ที่ค้างเก่าให้ราคาผิด ซึ่งแย่กว่าราคาที่แปลงมา**

ผลพลอยได้ทางวิศวกรรม: **`calcPrice` คิดเป็นบาทสกุลเดียวตลอดสายพาน** การแปลงเป็นเรื่องของชั้นแสดงผล
และตอนออกใบเสนอราคาเท่านั้น — ถ้าเป็น price list เครื่องคิดราคาต้องรู้จักสกุลเงินทั้งเส้น

**สี่เงื่อนไขที่ขาดไม่ได้:**

1. **อัตราตรึงในฐานข้อมูล ห้ามดึงสดจาก FX feed** — ลูกค้าที่เช็ควันอังคารแล้วกลับมาวันพฤหัสต้องเห็น
   ตัวเลขเดิม ไม่งั้นเขาเรียนรู้ว่าตัวเลขบนเว็บไม่จริง ซึ่งทำลายเหตุผลที่เว็บนี้มีอยู่
   อัปเดตอัตราเป็น**การกระทำที่ตั้งใจ** ไม่ใช่ผลข้างเคียง — และการตรึงอัตราก็คือ price list
   ที่มีตัวเลขเดียวแทนที่จะมี 98 ตัว สถาปัตยกรรมเดียวกัน ภาระคนละเรื่อง
2. **กฎปัดเศษต่อสกุล** ตั้งครั้งเดียว 9 กฎ ทุกสินค้าได้ตัวเลขสวยอัตโนมัติ
3. **ใบเสนอราคาล็อกอัตราที่ใช้** ไม่ใช่แค่ล็อกราคา — ใบที่ออกวันนี้เปิดเดือนหน้าต้องเป็นยอดเดิม
4. **แยก `minorExponent` (ข้อเท็จจริงของสกุล) ออกจาก `roundTo` (นโยบาย)** — ดูข้อ 4.3(ค)

ตัวอย่างจากแคตตาล็อกจริง `awn-4t` 320×160 = **฿7,680** *(อัตราด้านล่างเป็นตัวอย่างประกอบเท่านั้น)*

| | ดิบ | ปัดตามกฎ |
|---|---|---|
| VND ปัดขึ้นหลักพัน | ₫5,990,400 | **₫5,991,000** |
| USD ปัดหลักหน่วย | $236.54 | **$237** |
| MYR ปัดหลักหน่วย | RM 998.40 | **RM 998** |

**จุดเดียวที่โมเดลนี้พัง** คือตอนที่ตลาดหนึ่งมีต้นทุนต่างจริง (ส่งเวียงจันทน์แพงกว่าส่งพิษณุโลก)
แก้ได้โดยให้อัตราแบกส่วนต่างตลาดไว้ — ยังเป็นตัวเลขเดียวต่อตลาด

⚠️ **แต่วินาทีที่อัตราไม่ใช่ FX บริสุทธิ์ จะเกิดช่องอาร์บิทราจทันที** ลูกค้าไทยกดเลือกสกุลที่ถูกที่สุดได้
ตอนนั้น **สกุลเงินต้องผูกกับปลายทางจัดส่ง ไม่ใช่ผูกกับ dropdown** ส่วน dropdown เหลือไว้ดูเฉยๆ
พร้อมป้าย "ราคาโดยประมาณ" — ตราบใดที่อัตรายังเป็น FX ตรงๆ ปัญหานี้ไม่มี

```sql
-- 9 แถว แทนที่จะเป็น 882 · append-only เพื่อให้ตรวจใบเสนอราคาย้อนหลังได้
currency_rates (
  currency        char(3),
  minor_exponent  smallint,     -- 0 = VND/LAK · 2 = ที่เหลือ
  rate_micro      bigint,       -- สตางค์ -> หน่วยย่อยปลายทาง ที่ความละเอียด 1e-6
  round_to_minor  bigint,       -- นับเป็น "หน่วยย่อย" เสมอ · VND exponent 0 → 1000 = ปัดหลักพันดอง
  round_mode      text,         -- up | half_up
  effective_from  timestamptz
)
```

Postgres สำหรับตัวเงินอื่นๆ: `bigint` minor units + คอลัมน์ currency ชัดเจน
(**ไม่ใช่** `numeric` ไม่ใช่ `double precision`) · percent delta เก็บเป็น **basis points จำนวนเต็ม**
และ**ไม่เกี่ยวกับสกุลเงิน** — 8% ก็ 8% ทุกที่ (มีแค่ 3 ค่าในแคตตาล็อกทั้งหมด)

### 4.3 สามกับดักที่ตรวจเจอพร้อมตัวเลขจริง

**(ก) ปัดแบบ ceil ทั้งกระดานขัดกับเทสต์ที่มีอยู่**

spec case 6 คือ ฿8,791.2 — `ceil` ที่หน่วย ฿1 ได้ 8,792 แต่ `tests/pricing.test.ts:115` ปักไว้ `toBe(8791)` (ยืนยันแล้ว)

> **ตัดสินแล้ว: THB คงเป็น `half_up`** ตัวเลข THB ทุกตัวในเทสต์ปัจจุบันต้องถูกรักษาไว้เป๊ะ

ผลที่ตามมาสำคัญกว่าที่คิด — เฟส 1 เปลี่ยนจาก "เขียนเทสต์ราคาใหม่ทั้งชุด" เป็น**การแปลงเชิงกลที่ตรวจสอบได้**
`expect(price.total).toBe(8791)` → `expect(price.totalMinor).toBe(879100)` ปลอดภัยขึ้นมาก

**(ข) ยอดรายบรรทัดไม่บวกได้ยอดรวม**

ถ้าปัดทีละบรรทัดแล้วเอายอดรวมจาก sum ที่ไม่ปัด รายการจะไม่ foot ตัวอย่างจริงที่คำนวณไว้: VND 3 บรรทัด ปัดทีละบรรทัดรวมได้ ₫20,247,000 แต่ผลรวมที่แม่นคือ ₫20,245,000 — ต่างกัน ₫2,000 หลัง VAT

โมเดลสกุลเดียวไม่ได้ทำให้ปัญหานี้หายไป มันแค่ย้ายที่ — ตอนนี้มีการปัด **สองชั้น**: บาทหนึ่งครั้ง
แล้วสกุลปลายทางอีกครั้ง ลำดับที่ถูกคือ

```
1. คำนวณแต่ละบรรทัดเป็นบาทแบบ exact  →  ปัดเป็นสตางค์/บาทตามกฎ THB  =  line.total_thb
2. แปลง line.total_thb แต่ละบรรทัด    →  ปัดตามกฎของสกุลปลายทาง      =  line.total_display
3. net = SUM(line.total_display)  ← บวกจากบรรทัดที่ปัดแล้ว ไม่ใช่แปลงยอดรวม
4. ภาษีคิดจาก net นี้
```

→ **เลือกจุดปัดจุดเดียวต่อชั้น** ตัวเลขที่อยู่บนสัญญาคือยอดรายบรรทัด ส่วน `unitPrice`
เป็น**ตัวเลขแสดงผลที่บวกกันไม่ได้** ต้องประกาศไว้ให้ชัดในโค้ดและใน UI

**(ค) VND/LAK ไม่มีทศนิยม — สับสน 100 เท่าได้ง่ายมาก**

`minorExponent` (ข้อเท็จจริงของสกุลเงิน) กับ `roundToMinor` (นโยบายธุรกิจ) เป็นคนละเรื่อง `Math.round` ปัจจุบันรวมสองอย่างนี้เข้าด้วยกัน ต้องแยก และต้องมีเทสต์ยืนยันว่า `roundToMinor / 10^minorExponent` เท่ากับหน่วยที่ตั้งใจจริงทั้ง 9 สกุล

### 4.4 VAT — ตั้งค่าได้ แต่มีหนึ่งอย่างที่ห้ามตั้งค่า

> **ตัดสินแล้ว** VAT ตั้งค่าได้

**"ตั้งค่าได้" ตอบคำถามเรื่องอัตรา แต่ยังไม่ตอบคำถามที่บล็อกเฟส 1 อยู่** — สิ่งที่บล็อกคือ *ยอดที่มัดจำ % คิดจากมันรวม VAT หรือยัง* ซึ่งถ้าปล่อยให้ตั้งค่ารายใบ **ฐานยื่น ภ.พ.30 จะกลายเป็นช่องที่ฝ่ายขายพิมพ์เอง**

→ ทางออกคือ**เก็บสามคอลัมน์เสมอ** แล้วคำถาม inclusive/exclusive จะหายไปจากชั้นจัดเก็บทั้งหมด

```
net_minor          ฐานภาษี — ผลของ calcPrice + override
vat_minor          ภาษี     — derive เสมอ ไม่มีใครพิมพ์
grand_total_minor  = net + vat   ← ยอดที่ลูกค้าโอน
```

| | |
|---|---|
| **ตั้งค่าได้** | อัตรา (`vat_rate_bp`) · ประเภท (`standard` / `zero_rated` / `exempt` / `out_of_scope`) · แต่ละบรรทัดและแต่ละค่าบริการเสียภาษีหรือไม่ · **วิธีกรอก** (ฝ่ายขายพิมพ์ยอดก่อน VAT หรือยอดรวม VAT) |
| **ห้ามตั้งค่า** | **`grand_total_minor` รวม VAT เสมอ** — งวด มัดจำ การริบ การคืนเงิน อ้างถึงตัวนี้ตัวเดียวทั้งระบบ · `vat_minor` เป็นค่า derive เท่านั้น |

การกรอกทั้งสองทางให้ผลที่ foot เหมือนกัน:

```
กรอกยอดก่อน VAT ฿8,791   → vat = round(8791 × 700/10000) = ฿615.37 → grand = ฿9,406.37
กรอกยอดรวม VAT ฿10,000   → net = round(10000 × 10000/10700) = ฿9,345.79 → vat = ฿654.21
                            (คิด vat จากส่วนต่าง ไม่ใช่คูณตรง เพื่อให้ foot เสมอ)
```

⚠️ **ผลที่ตามมาทันที** — ตัวอย่างในข้อ 7.5(จ) และ 7.8 ที่เขียนไว้ด้วยยอดก่อน VAT ต้องอ่านใหม่เป็นยอดรวม VAT: มัดจำ 30% ของ ฿8,791 คือ **฿2,822 ไม่ใช่ ฿2,637** และ `"ราคายังไม่รวม VAT 7%"` ที่เป็นข้อความคงที่ 8 จุดใน 7 ไฟล์ ต้องกลายเป็นค่าที่ render จาก `vat_rate_bp` และประเภทของใบนั้น

**และการคืนเงินต้องออกใบลดหนี้** เพราะยอดที่คืนมีส่วน VAT อยู่ในนั้น (ข้อ 7.12)

### 4.5 ข้อมูลที่ค้างอยู่จะถูกตีความผิดเงียบๆ

**สองจุด และทั้งคู่เงียบสนิท:**

### 4.6 สิ่งที่เฟส 1 เจอจริง

**🔴 v1.0.0 คิดเงินขาดไป ฿1 ใน 87 ชุดค่า** — จากการเทียบ 55,000+ ชุดกับ `calcPrice` ของ v1.0.0 ที่ vendor ไว้ใน `tests/baseline/`

```
ราคาจริงลงท้าย .50 เป๊ะ   เช่น ฿15,718.50
float ของ v1 ได้           15718.4999999999982   →  Math.round → 15718
เลขจำนวนเต็มได้            15718.50              →  half_up   → 15719
```

พิสูจน์แล้วว่า **ทั้ง 87 ชุดมีเศษเป็นครึ่งบาทพอดี** ไม่ใช่ค่าใกล้เคียง — เป็นคลาสเดียวล้วน
เทสต์ `pricing-parity` **ตรึงเลข 87 ไว้** ไม่ใช่ปล่อยผ่านแบบหลวม ถ้าตัวเลขนี้ขยับแปลว่ามีคนเปลี่ยนราคาและต้องพูดออกมา

> half_up คือกฎที่ยืนยันแล้ว ดังนั้นเลขใหม่ถูก และของเดิมผิด — แต่ **ราคา 87 ชุดขึ้น ฿1** ต้องรู้ตัว ไม่ใช่ค้นพบทีหลัง

**🐛 กับดักที่ผมสร้างเองแล้วเทสต์จับได้: double rounding** — ปัด scaled → สตางค์ → บาท ทำให้ ฿36,224.496 กลายเป็น ฿36,224.50 ระหว่างทางแล้วขึ้นเป็น ฿36,225 · แผนข้อ 4.3(ข) เขียนกฎ **"จุดปัดจุดเดียวต่อชั้น"** ไว้เองแล้วผมใส่สองจุด → แก้เป็นปัดครั้งเดียวจากความละเอียดเต็มตรงไปยังหน่วยแสดงผล

**ผลพลอยได้ที่วัดได้**

- `NaN` และ `-0` **แทนค่าไม่ได้อีกต่อไป** — `bigint` ไม่มีทั้งสองค่า · `+ 0` ที่ v1 ต้องใส่ใน `pricing.ts` หายไปพร้อมเหตุผลของมัน
- พื้นที่เป็นจำนวนเต็มแท้: `มม. × มม. = µm²` ไม่มีการหารเลยจนถึงขั้นตอนสุดท้าย
- **`unitPriceScaledMinor`** เก็บราคาต่อหน่วยที่ความละเอียดเต็ม เพราะการแก้จำนวนทีหลังต้องคำนวณจากค่าเต็ม ไม่ใช่จากค่าที่ปัดแล้ว (ไม่งั้นเป็น double rounding รอบสอง)
- **`aluform.quote.v1` → `v2`** ใน commit เดียวกันตามข้อ 4.5 · ยืนยันในเบราว์เซอร์แล้วว่า payload v1 ที่ค้างอยู่ถูกเมินสนิท ไม่ถูกอ่านเป็นสตางค์
- `formatBaht` รับหน่วยย่อย ไม่ใช่บาท — การหารระหว่างทางไปหน้าจอคือจุดที่การตัดสินใจปัดเศษหลบสายตารีวิว

### 4.7 สิ่งที่เฟส 2 เจอจริง

**อันตรายจริงคือการ snap ใหม่ ไม่ใช่การแปลงหน่วย** — เทสต์หักล้างสมมติฐานตั้งต้นของผมเอง: 3,205,000 µm แปลงเป็นนิ้วแล้วกลับมาได้เป๊ะ เพราะ double มีความละเอียดพอ · สิ่งที่ทำให้ขนาดเปลี่ยนคือการ **snap** ตอนหน้าจอเป็นนิ้ว: 3,200,000 → 3,200,400 µm โตขึ้น 0.4 มม.

**กฎอัตราส่วนเคยจะเงียบทั้งช่วง [3,4)** — `(4805000n / 1600000n) === 3n` ทำให้ `> 3n` เป็นเท็จ ทั้งที่อัตราส่วนจริงคือ 3.0031 · เขียนใหม่เป็นคูณไขว้ `w > 3h` และยืนยันด้วยการรันว่ากฎยิงจริงที่ 3.0031 · **หน้าต่างที่ผลิตไม่ได้เกือบผ่านเข้าตะกร้าไปตัดจริง**

**baseline ที่คิดว่าแช่แข็งแล้ว ยังไม่ได้แช่แข็ง** — `pricing-v1.0.0.ts` import type จาก `src/types/catalog.ts` ที่ยังมีชีวิต จึงเปลี่ยนตามโค้ดปัจจุบันมาตลอด · แยกเป็น `catalog-v1.0.0.ts` แล้ว ตัวสูตรราคายังตรงกับ v1.0.0 ทุกบรรทัด

**mutation test เป็นด่านที่ขาดไป** — เทสต์ที่ผ่านไม่ได้แปลว่าจับได้ · ทดลองแอบเปลี่ยนราคาสองแบบแล้ว harness จับได้ทั้งคู่ รวมถึงเคสที่กลัวที่สุดคือ **สเกลพื้นที่ผิด 1e6** · มิวเทชันแรกที่ผมลอง (`+1n`) เล็กเกินไป — 1e-12 สตางค์ ต่ำกว่าเกณฑ์ปัดเศษ จึงไม่ได้พิสูจน์อะไรเลย

**ขั้น 7–8 เสร็จแล้ว** — ตัวเลือกหน่วย 5 หน่วยบนหน้าจอ และ `entered_unit` ที่บันทึกจริง
พิสูจน์ในเบราว์เซอร์: ทัวร์ cm → mm → m → in → ft → cm **ราคาคงที่ ฿7,692 ทุกจุดจอด** และค่ากลับมาเท่าเดิมเป๊ะ
นิ้วแสดงเป็นเศษส่วน `126 1/8"` ฟุตเป็น `10' 6 1/8"` · พิมพ์ 100.3" → snap **ขึ้น** เป็น 100 3/8" = 2,549,525 µm
และดูเป็น cm ได้ 254.9525 — **ไม่ปัดให้สวยเป็น 255** เพราะนั่นคือขนาดที่จะตัดจริง

**ขั้น 9 (`Issue` → `{key, params}`) เลื่อนไปเฟส 6 โดยตั้งใจ** — ทำตอนนี้คือเดา key scheme โดยไม่มีไฟล์ 8 ภาษาให้ตรวจ

**ลิงก์เก่าถูกปฏิเสธทั้งใบ ไม่ใช่ clamp** — `?width=320.5` ที่ไม่มี `v=3` ตกไปที่ค่า default ของสินค้า ไม่ใช่ถูก clamp ขึ้นเป็น 60 ซม. · clamp คือกลไกที่แปลงข้อมูลผิดหน่วยให้กลายเป็นข้อมูลที่ดูถูกต้อง

## 5. Catalog schema

### สองชั้น: ตาราง normalise สำหรับแก้ไข + เอกสาร JSONB ที่แช่แข็งสำหรับอ่าน

ตาราง normalise (`products` / `option_groups` / `option_values` / `product_version_options`) เป็นพื้นผิวที่ dashboard แก้ — ตอบโจทย์ "แก้ option ทีละตัว" ที่ whole-entity PUT ทำไม่ได้

เอกสาร JSONB ที่ compile แล้วเป็นพื้นผิวที่ web/api อ่านและที่ order อ้างถึง — เปลี่ยนไม่ได้เมื่อ publish แล้ว

**rule AST อยู่ใน JSONB** พร้อมคอลัมน์ `referenced_group_codes text[]` ข้างๆ เป็นด้ามจับให้ตรวจ integrity ได้ · **elevation อยู่ใน JSONB ก้อนเดียว** อย่า normalise panel

### ห้าจุดที่ต้องระวัง

1. **ลำดับ statement ตอน publish** — partial unique index `WHERE status='published'` ถูกตรวจทีละแถวตอน insert ไม่ใช่ตอน commit **ต้อง archive ตัวเก่าก่อน แล้วค่อย publish ตัวใหม่** พร้อม `SELECT ... FOR UPDATE` กันแข่งกัน
2. **สต็อกกับการแช่แข็ง** — ถ้า `available` อยู่บนแถวที่แช่แข็งแล้ว จะปรับสต็อกไม่ได้เลย ต้องแยกออกมาหรือ scope trigger เฉพาะคอลัมน์
3. **invariant ข้าม entity ต้องอยู่ใน DB ไม่ใช่ zod** — `parseCatalog` ตรวจ slug ซ้ำ / id ซ้ำ / **`skuPrefix` ซ้ำ** / categoryId ไม่มีอยู่ ซึ่ง `productSchema` ตัวเดียวตรวจไม่ได้ → เป็น `UNIQUE` และ `FK` ใน Postgres
4. **`.omit().superRefine()` ไม่ compile** — refinement ปัจจุบันอ่าน `product.id` ใน 4 จาก 5 ข้อความ ต้องทำให้ id-agnostic ก่อน
5. **ปิดวงระหว่างหน้าจอกับ API** — ส่ง `productVersionId` + `documentHash` ลงไปกับ Product ที่ resolve แล้ว และบังคับให้แนบกลับมาทุกครั้งที่ขอราคา/สั่งซื้อ **API ตอบ 409 พร้อมเอกสารใหม่เมื่อไม่ตรง** ไม่งั้นลูกค้าตั้งค่าอยู่ 5 นาทีระหว่างที่มีการ publish เวอร์ชันใหม่ แล้วถูกคิดราคาจากเอกสารคนละฉบับกับที่เห็น

### `Issue` ต้องเลิกเป็นข้อความ

`validation.ts:204` **สร้าง**ข้อความขึ้นมาเอง ไม่ใช่แค่ส่งผ่าน:
```ts
`${group.labelTh}ต้องอยู่ระหว่าง ${group.min}–${group.max} ${group.unit}`
```
→ `Issue` ต้องเป็น `{ key, params }` และ `PriceBreakdown.lines[].label` เช่นกัน กระทบ `validation.ts` · `optionStates.ts` · `quoteReducer.ts` · `IssuePanel` · `PriceBreakdownList` และ assertion ในเทสต์ ต้องตั้งงบเวลาไว้

### สี่ช่องโหว่ด้านความปลอดภัยที่ตรวจเจอ

**(ก) account pre-hijacking** — ห้าม link บัญชีด้วยอีเมลที่ยังไม่ยืนยัน ถ้าผู้โจมตีสมัครไว้ก่อนด้วยอีเมลของเหยื่อ (ยังไม่ยืนยัน) แล้วเหยื่อล็อกอินด้วย Google อีเมลเดียวกัน การ merge เข้าบัญชีเดิมคือการยกบัญชีให้ผู้โจมตี
→ พิสูจน์การครองอีเมลแล้วต้อง**ถอดอีเมลออกจากบัญชีที่ยังไม่ยืนยันทุกใบ** แล้วสร้างบัญชีใหม่ ไม่ใช่ merge

**(ข) OAuth `state` ต้องผูกกับเบราว์เซอร์** — เก็บ state ไว้ฝั่ง server อย่างเดียวคือการถอด CSRF protection ทั้งหมดออก ผู้โจมตีเริ่ม flow เอง ล็อกอินด้วยบัญชีตัวเอง แล้วหลอกให้เบราว์เซอร์เหยื่อเปิด callback → เหยื่อถูกล็อกอินเข้าบัญชีผู้โจมตี
→ เก็บแถวฝั่ง server **บวก** cookie ผูกเบราว์เซอร์ (`httpOnly`, `Secure`, `SameSite=None` เพราะ Apple ใช้ cross-site POST)

**(ค) refresh rotation แข่งกัน** — dashboard ยิง API ขนานกันหลายเส้น พอ token หมดอายุพร้อมกันทุกเส้นจะ refresh พร้อมกัน แล้วระบบจะมองว่าเป็นการใช้ token ซ้ำ → เตะผู้ใช้ออกกลางงาน
→ rotation ต้องเป็น **statement เดียวแบบ atomic** พร้อมช่วงผ่อนผัน ~15 วินาที

**(ง) boot แล้ว refuse to start เมื่อ permission ไม่ตรง จะทำให้ rollback พัง** — release N+1 เพิ่ม permission ใหม่ลง DB พอ rollback กลับ N โค้ดเก่าจะไม่รู้จัก permission นั้นแล้วไม่ยอมบูต
→ **แยกทิศทาง**: ขาดใน DB → upsert ตอนบูต (ปลอดภัย เดินหน้าอย่างเดียว) · เกินใน DB → log warning ย้ายการตรวจเข้มไป CI

### guest cart ไม่เข้ากับกฎ "ทุก query ต้องมี scope"

ผู้เยี่ยมชมนิรนามไม่มี user ไม่มี group ไม่มี permission — แต่**เป็นช่องทางหลักของ funnel** ต้องมี scope variant ที่สี่คือ `{ kind: 'guest', guestId }` ไม่งั้นเส้นทางนิรนามทั้งเส้นแสดงออกมาในระบบไม่ได้เลย

### สิทธิ์ ≠ เมนู (คงจากร่างแรก)

permission เป็นแหล่งความจริงเดียว เมนู derive จากมัน **API ต้อง enforce ทุก endpoint** พร้อม boot-time route audit ที่ทำให้ endpoint ใหม่ที่ลืมใส่ guard บูตไม่ผ่าน

## 7. Order และการชำระเงิน

> **ตัดสินแล้ว** ชำระเงินด้วยการอัปโหลดสลิปแล้วฝ่ายขายกดยืนยัน · ต้องมียกเลิก ตีกลับ และปฏิเสธสลิป

### 7.1 เก้าสถานะ ไม่ใช่หก

โจทย์ให้มา 6 สถานะ การเพิ่มยกเลิก/ตีกลับต้องการอีก 3 และแต่ละตัวมีเหตุผลของตัวเอง

| สถานะเพิ่ม | ทำไมแยกออกมา |
|---|---|
| `redesign` | แยกจาก `draft` เพราะ invariant ตรงข้ามกัน — draft ไม่มีสัญญา ไม่มีเงิน ไม่มีประวัติผลิต ส่วน redesign มีครบสามอย่าง ถ้าใช้ชื่อเดียวกัน ทุก query ที่ถามหา "ตะกร้าที่ยังไม่ขาย" ต้องจำใส่ `AND contract_id IS NULL` แล้ววันหนึ่งจะมีคนลืม |
| `cancelled` | terminal |
| `superseded` | **แยกจาก `cancelled`** ไม่งั้นการแก้ไขหลัง freeze ทุกครั้งจะไปโผล่ในรายงานยกเลิกว่าเป็นยอดขายที่หลุดมือ ตัวเลขที่ฝ่ายขายดูจริงจะผิดตั้งแต่วันแรก |

เก็บเป็น `text` + `CHECK` **ไม่ใช่ pg enum** — โจทย์นี้เพิ่งงอกสถานะมาอีก 3 ตัวหลังจากบอกว่าครบแล้ว ให้สมมติว่าจะมีอีก และ `ALTER TYPE ... ADD VALUE` ถอนคืนไม่ได้

### 7.2 การตีกลับ — guard ที่ผมเกือบใส่กลับด้าน

ผู้ออกแบบเสนอ guard ว่า "ราคาที่คำนวณใหม่ต้องไม่เกินสัญญาเดิม" ผู้ตรวจสอบชี้ว่า**กลับด้าน**

> แบบที่ผลิตไม่ได้ มักแก้ด้วยของที่**แพงขึ้น** — โปรไฟล์หนาขึ้น เปลี่ยนเป็นกระจกสองชั้น เพิ่มจุดล็อก
> guard นั้นจะบล็อกเคสที่มันถูกสร้างมาเพื่อรองรับพอดี

→ guard ที่ถูกคือ **guard ที่ขอบเขต ไม่ใช่ที่ราคา** — สินค้าเดิม ช่องเปิดไม่ใหญ่ขึ้น ไม่มีบรรทัดที่ลูกค้าไม่ได้สั่ง ส่วนต่างราคาบริษัทรับไว้เอง (บันทึกเป็น `absorbed_delta` เพื่อให้เห็นต้นทุนคุณภาพ)

**ถ้าส่วนต่างใหญ่เกินรับไหว** → ใช้กลไก revision เดิม: order เดิมเป็น `superseded` เกิด order ใหม่ที่ลูกค้าต้องอนุมัติ

### 7.3 ปฏิเสธสลิป ไม่ใช่ transition ของ order

ความไม่สมมาตรนี้คือตัวออกแบบ: **ยืนยันสลิป = transition** (`awaiting_payment → production_confirmed`) แต่ **ปฏิเสธสลิป = เหตุการณ์ระดับ payment** order ยังอยู่ที่ `awaiting_payment` เหมือนเดิม

ถ้าทำให้การปฏิเสธเป็น transition จะต้องประดิษฐ์สถานะที่มีความหมายเท่ากับสถานะก่อนหน้า ซึ่งเป็นยาพิษ

> พอมีมัดจำก็มีสลิปมากกว่าหนึ่งใบ **"ยืนยันสลิป" ที่เป็น transition คือใบที่ปิดงวดซึ่งถือประตู** ใบอื่นไม่ขยับ order — ดูข้อ 7.5(ข)

### 7.4 เจ็ดกับดักที่ตรวจเจอ — ต้องไม่ทำซ้ำ

1. **FK วนกัน** `orders.status_event_id → order_events.id` และ `order_events.order_id → orders.id` ทั้งคู่ `NOT NULL` **สร้าง order ไม่ได้เลย** → ต้อง deferrable หรือ nullable ตอน insert
2. **authorization ตรวจแค่ *ประเภท* ผู้กระทำ** — `actors: ['customer']` ไม่ได้แปลว่า "ลูกค้าคนนี้" ลูกค้าที่ล็อกอินคนไหนก็ยกเลิก order ของคนอื่นได้ถ้ารู้ id → **ความเป็นเจ้าของต้องอยู่ใน query ที่โหลด order** ไม่ใช่เช็คทีหลัง
3. **ไม่มีอะไรถูก pin ระหว่าง submit กับ accept** — ฝ่ายขายดูสลิปอีกหลายชั่วโมงหรือหลายวันถัดมา ถ้ามีการ publish catalog เวอร์ชันใหม่คั่น สัญญาจะถูกสร้างจากเอกสารคนละฉบับกับที่ลูกค้าเห็น → **pin `catalog_version_id` + `rate_id` ตอน `submit_for_payment`**
4. **`Array.find` เลือก transition ผิดตัว** — `cancel` มีสองแถว (ก่อน/หลัง freeze) ถ้า controller หา schema ก่อนโหลด order zod จะ **strip** ฟิลด์ที่จำเป็นของการยกเลิกหลัง freeze ทิ้งเงียบๆ → โหลด order และจับ lock **ก่อน** เลือก payload schema
5. **`request_change` ไม่มีอะไรมาเคลียร์** — คำขอแรกของลูกค้าค้างถาวร บล็อกคำขอต่อไปตลอดอายุ order
6. **อัปโหลดสลิปไม่มี guard ที่สถานะ** — `FOR UPDATE` แค่จัดลำดับการแข่ง ไม่ได้ห้าม สลิปยังถูก insert หลัง accept commit ไปแล้ว
7. ~~**order ฉบับแก้ไขไม่รับเงินที่จ่ายมาแล้ว**~~ — ไม่มี refund API เพราะจ่ายด้วยมือ ลูกค้าจะถูกเรียกเก็บยอดใหม่เต็มจำนวน → **ออกแบบแล้วในข้อ 7.8** (ยกเป็น allocation ที่ชี้กลับต้นทาง)

### 7.5 มัดจำ — การชำระเป็นงวด

> **ร้องขอเพิ่ม** รองรับการวางมัดจำ · ออกแบบรอบนี้ผ่าน 6 agent + ผู้ตรวจสอบฝ่ายตรงข้าม 3 ด้าน (blocking 19 ข้อ)

โจทย์เขียนขั้นตอนชำระเงินไว้ขั้นเดียว แต่งานสั่งทำเก็บมัดจำก่อนแล้วเก็บส่วนที่เหลือ — **สร้างเป็น collection ตั้งแต่แรก ใช้แถวเดียวถ้าพอ** เพิ่มทีหลังเจ็บกว่ามาก

#### ก. งวดหนึ่งงวด = ฐานคิดเงิน + ประตู

แยกสองเรื่องนี้ออกจากกัน แล้วเคสสุดขอบหายไปเองโดยไม่ต้องเขียน `if`

| ส่วน | ค่า | ความหมาย |
|---|---|---|
| **basis** | `percent` (bp) · `fixed` · `remainder` | คิดยอดงวดยังไง — **`remainder` มีได้ตัวเดียวและต้องเป็นตัวสุดท้าย** |
| **gate** | `gates_entry_to` (สถานะ หรือ `NULL`) | ชำระครบแล้วเปิดทางเข้าสถานะไหน |

ผลที่ได้ฟรี: **ไม่มีมัดจำ** = แถวเดียว `remainder` + `gates_entry_to='production_confirmed'` · **มัดจำ 100%** = แถวเดียวเหมือนกัน · **30/70** = สองแถว งวดแรก `percent 3000` มีประตู งวดที่สอง `remainder` ไม่มีประตู หรือมีที่ `awaiting_installation` — ทั้งสามเคสเดินโค้ดเส้นเดียวกัน

**การแบ่งงวดต้อง foot** — ยืนยันด้วยยอดจริงจากเทสต์ (`tests/pricing.test.ts`):

```
฿8,791 แบ่ง 50/50 ด้วย half_up  →  ฿4,396 + ฿4,396 = ฿8,792   ผิดไป ฿1
งวดสุดท้ายเป็นเศษที่เหลือ        →  ฿4,396 + ฿4,395 = ฿8,791   ตรง
฿8,791 มัดจำ 30%                →  ฿2,637 + ฿6,154 = ฿8,791   ตรง
```

→ งวด 1..n-1 ปัดตามกฎ **งวดสุดท้ายคือส่วนต่าง** + `assert_schedule_foots()`: `SUM(due_minor) = orders.total_minor`
**ยกเว้น order ที่จบแล้ว** — `cancelled` / `superseded` ต้องมี `schedule_closed_at` และหลุดจาก assertion นี้ ไม่งั้นการยกเลิกหลังรับมัดจำจะละเมิด constraint และ**แก้ไม่ได้โดยไม่ migrate**

#### ข. มัดจำไม่ได้ย้ายจุด freeze มันเปลี่ยน*เงื่อนไข*ที่เปิดจุดนั้น

จุด freeze ยังเป็นการเข้า `production_confirmed` เหมือนเดิม สิ่งที่เปลี่ยนคือเดิมต้องจ่ายครบ ตอนนี้จ่ายงวดที่มีประตูก็พอ

ข้อ 7.3 บอกว่า "ยืนยันสลิป = transition" ซึ่งกำกวมทันทีที่มีสองสลิป → **ระบุให้ชัด: ยืนยันสลิปที่ทำให้งวด *ที่ถือประตู* ครบ คือ transition · สลิปงวดอื่นเป็นเหตุการณ์ระดับ payment ไม่ขยับ order** (สมมาตรกับการปฏิเสธสลิปในข้อ 7.3)

**ห้ามเพิ่มสถานะ `awaiting_balance`** — มันจะเป็นสถานะที่ขนานไปกับ `in_production` ทุกประการ ต่างแค่ยอดค้าง ซึ่งเป็นข้อมูลของ payment ไม่ใช่ของ order · ยอดค้างเป็น**คุณสมบัติที่ derive ได้** ไม่ใช่สถานะ

#### ค. frontier เป็น `seq` ไม่ใช่จำนวนงวด

`settledThrough = MAX(seq) ของ prefix ที่ชำระครบ` (ถ้ายังไม่มีอะไรครบ = `MIN(seq) - 1`) — เขียนครั้งเดียว ใช้ทั้ง SQL และ TS ห้ามมีสองสูตร ห้าม `COUNT(*)` และ**บังคับ `seq >= 1` ด้วย CHECK** เพราะสูตรสองแบบให้คำตอบต่างกันทันทีที่ `seq` ไม่ต่อเนื่องจาก 1

**และประตูที่เปิดแล้วปิดได้** — งวด `remainder` ล็อกไม่ได้ตามนิยาม (มันคือตัวรับส่วนต่าง) ถ้าราคาขยับขึ้นหลังชำระครบ `settledThrough` จะถอยหลัง → **อย่าประเมินประตูจากเงินอย่างเดียว** ใช้ `เคยเข้าสถานะนี้แล้ว (order_events) OR ประตูเงินเปิดอยู่ตอนนี้`

#### ง. recompute: ล็อกที่จ่ายแล้ว งวดท้ายรับส่วนต่าง

`awaiting_payment` และ `redesign` เป็นสถานะที่**แก้ไขได้** แปลว่ายอดเปลี่ยนได้ทั้งที่เงินเข้ามาแล้ว

1. งวดที่มีเงินแตะแล้ว → `locked_due_minor = due_minor` แก้ไม่ได้ (`ON DELETE RESTRICT` จาก money posting)
2. งวดที่ยังไม่แตะ → คำนวณใหม่จาก basis
3. `remainder` ดูดส่วนต่างทั้งหมด
4. ถ้าส่วนต่างทำให้ `remainder` ติดลบ → ยอดใหม่ต่ำกว่าเงินที่รับมาแล้ว ต้องเข้ากระบวนการคืนเงิน (ข้อ 7.8) **ห้ามปล่อยให้งวดติดลบ**

บริการ recompute ต้องรับ `draft | awaiting_payment | redesign` **ไม่ใช่ `awaiting_payment` อย่างเดียว** — งานตีกลับจากฝ่ายผลิตไปที่ `redesign` เสมอ และข้อ 7.2 บอกเองว่าการแก้มัก*แพงขึ้น*

#### จ. ~~🚧 ตัวบล็อก~~ VAT — **ตอบแล้วในข้อ 4.4** (ยอด `grand_total` รวม VAT เสมอ · อัตราและประเภทตั้งค่าได้)

มัดจำคือ % ของ**ยอดที่ลูกค้าโอนจริง** ซึ่งเป็นยอดรวม VAT แต่ในโค้ดปัจจุบัน `"ราคายังไม่รวม VAT 7%"` เป็น **ข้อความคงที่ 7 จุด** (`AppFooter` · `PriceSummary` · `Home` ×2 · `About` · `Quote` · `Configure`) — `pricing.ts` และ `quoteReducer.ts` ไม่มีเลขคำนวณ VAT สักบรรทัด

```
฿8,791 (ยังไม่รวม VAT) → มัดจำ 30% = ฿2,637
฿9,406.37 (รวม VAT)    → มัดจำ 30% = ฿2,822      ต่างกัน ฿185 ต่อออร์เดอร์เล็กหนึ่งใบ
```

→ **VAT ต้องเป็นบรรทัดที่คำนวณจริงใน `core` ก่อน** แล้วค่อยประกาศว่า `total_minor` ที่งวดอ้างถึงคือยอดรวม VAT (แนะนำ — เพราะเป็นยอดที่ปรากฏบนสลิป และสลิปคือหลักฐานเดียวที่ตรวจได้)

### 7.6 สลิป — สิ่งที่ต้องมีนอกจากตารางเก็บไฟล์

- **เก็บใน object storage ส่วนตัว อ่านผ่าน URL ที่มีอายุสั้นและถูก audit** ลูกค้าเห็นเฉพาะของตัวเอง
- **หน้าจอตรวจต้องเป็นการเทียบสองคอลัมน์ ไม่ใช่ปุ่ม "ยืนยัน"** — สลิปปลอมเป็นปัญหาที่รู้กันในไทย และการตรวจด้วยคนคือ**มาตรการควบคุมเดียว**ในโมเดลนี้ ต้องโชว์ยอดที่ควรได้เทียบกับสลิปให้เห็นความไม่ตรงทันที
- **PDPA** — สลิปมีเลขบัญชีและชื่อ **ลบภาพได้ แต่เก็บบัญชีแยกไว้** และแยกสิทธิ์ "ดู" ออกจาก "ดาวน์โหลด"
- **สกุลที่ชำระจริงต่างจากสกุลในสัญญา** — ใบแจ้งหนี้ USD ก็ยังโอนเข้าบัญชีบาท ตัวสะสมยอดต้องระบุชัดว่านับเป็นสกุลไหน ห้ามปนกัน
- **การกระทบยอด** — นำเข้า statement มาจับคู่กับสลิป แล้วทำให้ยอดที่จับคู่ไม่ได้เป็นสิ่งที่มองเห็น ไม่ใช่เงียบ

### 7.7 สิ่งที่การชำระด้วยมือประหยัดไป

ไม่มี webhook · ไม่มี reconciliation อัตโนมัติ · ไม่มี refund API · **ไม่มี PCI scope** · ไม่ต้องรองรับ payment method × 9 สกุล

แลกมาด้วย: การตรวจสลิปด้วยคนเป็นคอขวดและเป็นจุดเสี่ยงเดียว และการคืนเงินเป็นกระบวนการนอกระบบที่ต้องออกแบบแยก

### 7.8 เงินที่รับมาแล้ว เมื่อยกเลิก / แก้ไข / ตีกลับ

มัดจำทำให้ทุกเส้นทางในข้อ 7.1–7.2 กลายเป็นเส้นทางที่**มีเงินอยู่ในมือบริษัทแล้ว** ซึ่งร่างเดิมไม่ได้ออกแบบไว้ (ข้อ 7.4 ข้อ 7 เขียนไว้ว่าเป็นปัญหา — นี่คือคำตอบ)

**บัญชีแยกประเภทสองขา append-only** ไม่มีการ UPDATE ยอด · ทุกความเคลื่อนไหวเป็น posting คู่ระหว่าง `bank_thb` / `deposit_held` / `revenue` / `forfeited` / `credit_clearing` · ยอดคงเหลือของ order คือผลรวม ไม่ใช่คอลัมน์

**แยกให้ชัดว่ายอดไหนคืออะไร** — สามตัวนี้ต่างกัน และหน้าจอเดียวใช้ทั้งสาม

| ฟิลด์ | นิยาม | ทำไมต้องแยก |
|---|---|---|
| `paidMinor` | เงินสดที่รับจริง = ผลรวมสลิปที่ยืนยันแล้ว | ตัวเลขใหญ่สีมะนาวบนหน้าจอลูกค้า |
| `settledMinor` | ผลรวม allocation | ต่างจาก `paidMinor` เมื่อมีค่าธรรมเนียมธนาคารที่ตัดทิ้ง |
| `creditMinor` | เงินที่ยกมาจาก order ก่อนหน้า | ไม่ใช่เงินสดที่เข้ามาในรอบนี้ |

**การยกเลิกเมื่อมีเงินแล้ว** — เพดานการริบต้องผูกกับ*ภาระมัดจำ* ไม่ใช่กับเงินสดที่บังเอิญได้รับมา

```
฿18,432 · มัดจำ 30% = ฿5,530 · ลูกค้าจ่ายครบทั้งก้อนล่วงหน้า แล้วยกเลิกที่ awaiting_installation
  ริบ = 100% ของเงินที่รับ  → ฿18,432   ริบเกินภาระที่ตกลงกันไว้ 3 เท่า
  ริบ = 100% ของภาระมัดจำ   → ฿5,530    ถูก คืน ฿12,902
```

→ `forfeitBase = min(receivedMinor, scheduledDepositMinor)` แล้วค่อยคูณ bps แล้ว clamp ด้วยเงินสดที่รับจริงอีกชั้น

- **`production_confirmed` ต้องริบ 0** — ตอนนั้นยังไม่มีอะไรถูกตัด อะลูมิเนียมถูกตัดใน `in_production` การริบเต็มที่*วินาทีที่ freeze* ทำให้ลูกค้าที่กดยืนยันแล้วเปลี่ยนใจใน 5 นาทีเสียเท่ากับลูกค้าที่รอจนของเสร็จ · เก็บ 10000 bps ไว้ตั้งแต่ `in_production` เป็นต้นไป
- **ตารางการริบต้องครบทุก (สถานะที่ยกเลิกได้ × ฝ่ายที่ผิด)** — ห้ามใช้ `'ANY'` เป็น wildcard ใน `UNIQUE(policyId, fromStatus, fault)` เพราะไม่มี CHECK ไหนนิยามมันได้ · ต้องมี CI assertion นับแถว และ `redesign` **เป็นสถานะที่ยกเลิกได้** อย่าลืม
- 🔒 **`fault` ห้ามรับจาก request body** — มันตัดสินว่าลูกค้าได้เงินคืนเท่าไร · `fault='customer'` เสมอเมื่อลูกค้าเป็นคนกดยกเลิก · `fault='company'` ตั้งได้เฉพาะ staff และเฉพาะ order ที่มีบันทึกการตีกลับจริง

**เงินยกไป order ฉบับแก้ไข (`superseded` → order ใหม่)** — ยกเป็น **allocation ที่ชี้กลับไปต้นทาง** (`carried_from_order_id`) **ไม่ใช่แถวงวดใบใหม่** ถ้าทำเป็นแถวงวด order เดิมจะยังรายงานว่าได้รับเงินก้อนนั้นอยู่ตลอดไป พร้อมกับใบใหม่ — เงินก้อนเดียวถูกนับสองที่ · การ fold ของใบใหม่ต้องอ่านสลิปจาก ancestor chain

⚠️ และเมื่อยกมาแล้ว **ตัวแยกสาขาต้องเป็น `held_minor` ไม่ใช่ `cash_minor`** — การยกเงินไม่มีขาเงินสด ใบใหม่จึงมี `cash = 0` ตลอดกาล ทุกการตัดสินใจที่ถาม "ได้รับเงินมาหรือยัง" จะตอบผิด

**การคืนเงินต้องมีหลักฐานแบบเดียวกับสลิป** — ไม่มี refund API แปลว่าการคืนเงินคือคนโอนเงินออก ต้อง:

1. `refunds.accrual_event_id NOT NULL` + CHECK ว่า `amount_minor` เท่ากับยอดที่ตั้งค้างไว้
2. **trigger แช่แข็ง `amount_minor` และทุกคอลัมน์ payee เมื่อสถานะพ้น `requested`** — ไม่งั้นอนุมัติ ฿3,594 แล้วแก้เป็น ฿359,400 พร้อมเปลี่ยนบัญชีปลายทางได้ การอนุมัติจะไม่อนุมัติอะไรเลย
3. ผู้อนุมัติ ≠ ผู้ขอ · ขาเงินสดเขียนได้เฉพาะตอน disburse พร้อมหลักฐาน

**อีกสองข้อที่ต้องมี CHECK ไม่ใช่วินัย**

- `SUM(slip_allocations.amount_minor) = slips.amount_minor` ต่อสลิปที่ยืนยันแล้ว (deferred) — ตอนนี้ผู้ตรวจสลิปพิมพ์ยอด allocation เองได้ ไม่มีอะไรผูกกับยอดบนสลิป จะเคลียร์งวดด้วยเงินที่ไม่มีอยู่จริงก็ได้
- คิวงานของฝ่ายขายต้องมีสาขา terminal เป็นบรรทัดแรก — ไม่งั้น order ที่ยกเลิกแล้วแต่ยังมีเงินค้างจะไปโผล่ในถัง "รอลูกค้าโอน" ตลอดไป และ**เงินค้างบน order ที่จบแล้วคือถังที่ต้องเห็น** ไม่ใช่ถังที่ต้องซ่อน

### 7.9 ใบเสนอราคาที่ฝ่ายขายแก้ไขได้ทุกค่า

> **มติเจ้าของกิจการ** (1) ฝ่ายขายกำหนดเงื่อนไขมัดจำเองรายใบ — 100% หรือ % หรือยอดเงิน หรืออื่นๆ
> (2) ลูกค้าต่างประเทศจ่ายเป็นสกุลตัวเอง ฝ่ายขายปรับแก้ได้ (3) ยกเลิกแล้วคืนเงินด้วยการโอนตามปกติ
> (4) **ขั้นตอนออกใบเสนอราคาต้องแก้ไขได้ทุกค่า**

สี่ข้อนี้เป็นหลักการเดียวกัน: **ฝ่ายขายคือผู้มีอำนาจ ระบบเป็นผู้บันทึก ไม่ใช่ผู้ตัดสิน**

**สิ่งที่แลกไป ต้องพูดให้ชัด** — ความเสี่ยงข้อ 1 เดิมป้องกันด้วย "api คิดราคาเองเสมอ แล้ว 409 เมื่อไม่ตรง" **มาตรการนั้นใช้ไม่ได้อีกต่อไป** เพราะยอดที่ถูกต้องไม่มีนิยามเชิงคำนวณแล้ว

→ คำถามเปลี่ยนจาก **"ยอดนี้ถูกไหม"** (ตอบไม่ได้) เป็น **"ยอดนี้มาจากใคร และได้รับอนุญาตหรือยัง"** (ตอบได้เสมอ และบังคับที่ api ได้จริง)

#### ก. สามชั้น ห้ามยุบรวม

| ชั้น | คืออะไร | ใครเขียน |
|---|---|---|
| `computed` | ผลของ `calcPrice()` จาก (product_version, selections, measures, qty) | เครื่องเท่านั้น — api คำนวณเองเสมอ ไม่รับตัวเลขจาก client |
| `override` | แถวใน `quote_overrides` เก็บ **ทั้ง** `computed_minor` และ `override_minor` | มนุษย์ที่มีอำนาจ ผ่าน endpoint ของตัวเอง |
| `document` | JSONB แช่แข็งตอน `submit_for_payment` + `document_hash` | ระบบ ตอน pin |

**`pricing.ts` ไม่ต้องแตะแม้แต่บรรทัดเดียว** — และนั่นคือเหตุผลที่ต้องแยกสามชั้น ถ้ายัด override เข้า `calcPrice` เทสต์ 219 ตัวจะเลิกเป็นตาข่ายนิรภัยทันที โดยเฉพาะ `tests/pricing.test.ts:214` ที่ยืนยันว่า `sum(lines) === unitPrice`

**override เป็นค่าแทนที่ (absolute) ผูกกับ baseline — ไม่ใช่ delta**
เก็บ `entered_as` และ `entered_value_text` = สิ่งที่มนุษย์พิมพ์จริง ("8500" หรือ "-15%") เพราะฝ่ายขายพูดกับลูกค้าว่า "เอา ฿8,500" ไม่ได้พูดว่า "ลด ฿291"

> ถ้าเก็บเป็น delta: บรรทัด ฿8,791 ลด −฿291 เป็น ฿8,500 · พรุ่งนี้แคตตาล็อกขยับเป็น ฿9,500 · delta ทำให้ราคากลายเป็น ฿9,209 เงียบๆ ทั้งที่สัญญาไว้ ฿8,500

#### ข. anchor เดียวต่อความหมายหนึ่ง

ช่องที่มีความสัมพันธ์ทางเลขคณิตกัน (ราคาต่อหน่วย · ยอดรวมบรรทัด · ส่วนลด %) ถ้าแก้ได้ทุกช่อง คำถาม "ตัวไหนชนะ" จะเกิดทุกครั้งและถูกตอบต่างกันในแต่ละ endpoint

→ **UI มีช่องราคาต่อหน่วยให้พิมพ์ตามที่สั่ง แต่ตอนเขียนลง DB normalise เป็น `line_total` เสมอ** แล้วบันทึก `entered_as='unit_price'` ไว้ให้ audit · `unitPrice` บนจอกลายเป็นค่า derive = `line_total / qty` และต้องติดป้ายว่าบวกกันไม่ได้ ตามข้อ 4.3(ข)

> qty 2 ที่ตั้ง unit = ฿9,000 **และ** total = ฿18,432 พร้อมกัน → ใบไม่ foot ฿432 และมัดจำ 30% คิดจากยอดไหนก็ผิดอีกทาง

#### ค. อะไรแก้ได้ / แก้ไม่ได้

| | |
|---|---|
| **แก้ได้แบบ input** (recompute ต่อ) | qty · ขนาด · การเลือก option |
| **แก้ได้แบบ override** | ยอดรวมบรรทัด · ส่วนลดระดับเอกสาร · ยอดรวมสุทธิ · lead time |
| **แก้ได้แบบแถวใหม่** | ค่าขนส่ง/ติดตั้ง/สำรวจ · บรรทัดอิสระที่ไม่ผูกสินค้า |

ทุกอย่างในช่อง "แก้ไม่ได้" ไม่ใช่ค่าที่มนุษย์ตั้งใจจะตั้ง — มันคือค่าที่ derive จากค่าที่แก้ได้อยู่แล้ว **ให้ทางเข้าเดียวต่อความหมายหนึ่ง**

⚠️ **คำอธิบายที่ฝ่ายขายพิมพ์ห้ามขึ้นใบสั่งผลิต** — ฝ่ายขายพิมพ์ "กระจกเทมเปอร์ 8 มม." บนบรรทัดที่ sku บอก T6 (6 มม.) ได้ · ใบสั่งผลิตต้อง render จาก sku + option ที่ resolve จาก catalog document เท่านั้น ข้อความฝ่ายขายติดป้าย "สำหรับลูกค้า"

#### จ. `409` เปลี่ยนจากตรวจตัวเลขเป็นตรวจที่มา

client ไม่เคยส่งยอดเงินขึ้นมา ส่งแค่ `{catalogVersionId, documentHash, quoteRevision}` · api: โหลด order + `FOR UPDATE` **ก่อน**เลือก payload schema (กับดัก 7.4 ข้อ 4) → catalog ไม่ตรง = `409 CATALOG_STALE` → revision ไม่ตรง = `409 QUOTE_STALE` → recompute baseline เทียบ `computed_minor` **ไม่ตรง = integrity alarm ไม่ใช่ 409** เพราะแปลว่า core เปลี่ยนพฤติกรรมใต้เอกสารที่ pin แล้ว

**ตอน pin ต้อง re-verify ทุก override ว่า baseline ยังตรง** — ถ้ามีการ publish แคตตาล็อกคั่น ให้บล็อกการ submit และบังคับยืนยันราคาใหม่ทีละบรรทัด

> ลดราคา ฿18,432 → ฿17,000 ตอนบ่าย · ทีมอื่น publish ราคาใหม่ ฿20,000 ตอนเย็น · ถ้าไม่ re-verify ระบบยังโชว์ ฿17,000 โดยไม่มีใครรู้ว่าตอนนี้มันคือส่วนลด 15% ไม่ใช่ 7.8%

### 7.10 ตารางงวดที่ฝ่ายขายกำหนดเอง

โครงสร้าง basis+gate ในข้อ 7.5 รองรับอยู่แล้ว ที่เพิ่มคือ**ชั้นการประพันธ์**

- **UI กับ schema เป็นคนละคำถาม** — schema รองรับ n งวด · UI เสนอ 3 แบบ (เต็มจำนวน / มัดจำ % / มัดจำยอดเงิน) + โหมด "กำหนดเอง" ที่ปลดล็อกได้
- **แก้ข้อ 7.5(ก)** — `remainder` "มีได้อย่างมากหนึ่งตัว ต้องเป็นตัวสุดท้าย และต้องมีเว้นแต่แถว percent/fixed foot พอดี" (เดิมเขียนว่าต้องมีเสมอ ซึ่งบล็อกตารางที่ฝ่ายขายกรอกยอดเป็นตัวเลขครบเอง)
- **มัดจำแบบยอดเงินกับแบบ % ต่างกันตอนราคาขยับ** — ฿8,791 มัดจำ 30% = ฿2,637 · ถ้าแก้ยอดเป็น ฿9,500 มัดจำเลื่อนเป็น ฿2,850 อัตโนมัติ · แต่มัดจำ "฿2,637" แบบ fixed อยู่นิ่ง แล้ว `remainder` ดูดส่วนต่างทั้งหมด **ทั้งสองถูก แต่ต้องบอกฝ่ายขายว่ากำลังเลือกอันไหน**
- 🔒 **ต้องมีพื้นขั้นต่ำของงวดที่ถือประตู** ไม่งั้นมัดจำ ฿1 เปิดสายการผลิตได้ · การอนุมัติตารางที่ต่ำกว่าพื้น หรือตารางที่**ไม่มีประตูเลย** (ผลิตก่อนได้เงิน = การให้เครดิต) ต้องเป็นสิทธิ์ที่แยกจากสิทธิ์ลดราคา
- **ลดยอดต่ำกว่าที่รับมาแล้วต้องเข้ากระบวนการคืนเงิน** ห้ามปล่อยงวดติดลบ

### 7.11 ลูกค้าต่างประเทศชำระเป็นสกุลของตัวเอง

> ⚠️ **มตินี้กลับด้านกับที่แผนเคยแนะนำในคำถามข้อ 6** (เดิมแนะนำออกใบแจ้งหนี้เป็นบาท) — เจ้าของกิจการตัดสินอีกทาง บันทึกไว้พร้อมต้นทุนที่คำแนะนำเดิมพยายามเลี่ยง

**สัญญาเป็นบาทเสมอ การนำเสนอเป็นสกุลลูกค้า** — `orders.grand_total_thb_minor` คือฐานเดียวของ ledger, VAT, การริบ และ `pricing.ts` · `grand_total_invoice_minor` + `invoice_currency` + `rate_id` เป็นชั้นแสดงผลที่ผูกพันกับลูกค้า ผลิตด้วยสายพาน 4.3(ข) คือ**ปัดต่อบรรทัดแล้วบวก ไม่ใช่แปลงยอดรวม**

🚫 **ห้าม derive บาทย้อนกลับจากยอดสกุลต่างประเทศ** — เป็นข้อผิดพลาดที่ดูไม่ออก:

```
฿8,791 → USD @ 30.80 → $271.00 → แปลงกลับ = ฿8,798.70
฿7.70 นี้จะไปนั่งบนใบกำกับภาษี เป็นฐาน VAT และเป็นฐานการริบ
ทั้งที่มันเป็นเศษของกริดดอลลาร์ ไม่ใช่ราคาสินค้า
```

**เงินที่ธนาคารเครดิตเข้ามา ≠ ยอดที่คำนวณจากอัตราที่ตรึงไว้ เสมอ** — ต่างกันเท่าสเปรดของธนาคารลูกค้า ประมาณ 2–3% (บนใบ ฿18,432 = ~฿500) นี่ไม่ใช่บั๊ก มันคือความจริงทางบัญชี ต้องมีบัญชี `settlement_variance` รองรับ พร้อม `variance_kind` แยกประเภท (`fx_spread` / `bank_fee` / `refund_fx`)

- **"ฝ่ายขายปรับแก้" คือปรับอะไร** → ปรับ**ยอดที่ยอมรับว่าปิดงวดได้** ไม่ใช่ปรับอัตราที่ตรึงไว้ (ซึ่งจะทำให้ใบอื่นเพี้ยนตาม) และการยอมรับยอดที่ขาดคือ**ส่วนลด** ต้องนับรวมในเพดานอำนาจเดียวกัน
- **สลิปถูกยืนยัน ≠ เงินเข้าบัญชี** สำหรับการโอนข้ามประเทศ (1–2 วันทำการ) → ต้องมีบัญชีพัก `remittance_in_transit` และ **ห้ามจ่ายเงินคืนออกในขณะที่ยอดในบัญชีพักยังไม่เป็นศูนย์** ไม่งั้นคืนเงินสดจริงสำหรับเงินที่ยังไม่เคยเข้า
- **หลุมอาร์บิทราจในข้อ 4.2 เปิดกลับ** ทันทีที่ฝ่ายขายปรับได้รายใบ → สกุลเงินต้องผูกกับปลายทางจัดส่ง การเลือกสกุลที่ไม่ตรงตลาดต้องเป็น override ที่ต้องอนุมัติและถูกนับในรายงาน
- 💰 **คุ้มหรือไม่ ต้องถามก่อนสร้าง** — สายชำระต่างประเทศเพิ่ม ~6 ตาราง + 2 บัญชีแยกประเภท + งานกระทบยอดประจำวัน + ดีเลย์ 1–2 วันต่อออร์เดอร์ เพื่อจัดการเงินราว ฿500/ใบ · **วันนี้ระบบมีสินค้า 81 ตัวและออร์เดอร์ศูนย์ใบ** ถ้าเดือนหนึ่งมีใบต่างประเทศไม่ถึงสิบใบ ให้ทำเฟสหลัง แล้วเฟสแรกออกใบเป็นบาทพร้อมป้าย "ราคาโดยประมาณ" ตามเดิม

### 7.12 การคืนเงินด้วยการโอนตามปกติ

**`refunds.currency = 'THB'` เสมอ** — บริษัทไม่เคยถือเงินสกุลอื่น จะคืนเป็นดองต้องไปซื้อดอง ซึ่งคือการรับความเสี่ยงค่าเงินที่ไม่มีใครตัดสินใจ

**แต่เพดานยอดคืนต้องคิดในสกุลที่รับมา แล้วแปลงด้วยอัตราตัวเดียวกับขาเข้า** ไม่งั้นการรับ-คืนครบรอบรั่วเท่าสเปรดทุกใบ

- ขาเข้าต้องมีสลิปจากลูกค้า + คนที่สองยืนยัน · **ขาออกต้องเข้มเท่ากัน** — ยอดและบัญชีปลายทางถูกแช่แข็งเมื่อพ้น `requested` ผู้อนุมัติ ≠ ผู้ขอ ผู้กดโอน ≠ ผู้อนุมัติ
- **คืนเข้าบัญชีที่จ่ายมาเป็นค่าตั้งต้น** — "ขอคืนเข้าอีกบัญชีหนึ่ง" คือประโยคที่มิจฉาชีพพูด ต้องเป็นเส้นทางที่ต้องอนุมัติแยกและขึ้นรายงาน
- **การคืนเงินไม่ใช่ transition ของ order** สมมาตรกับข้อ 7.3
- **อนุมัติแล้วยังไม่โอน = คำสัญญาที่บริษัทให้ไว้** ต้องเป็นบัญชี `refund_payable` และมีคิวที่มองเห็น ไม่ใช่ค้างเงียบเป็นเดือน
- 🚧 **ต้องมีใบลดหนี้** ถ้ายอดรวม VAT — การคืนเงินโดยไม่มีใบลดหนี้คือสิ่งที่ทำให้ผู้ทำบัญชีหยุดงาน · ผูกกับตัวบล็อก VAT โดยตรง

### 7.13 รอยต่อ — ต้องนิยามครั้งเดียวก่อนเขียนตารางใดๆ

ออกแบบสี่ด้านแยกกันแล้วตรวจแบบปรปักษ์ (14 agent · blocking 57 ข้อ · ทุกด้าน needs-revision) **ปัญหาใหญ่ที่สุดไม่ใช่บั๊กรายข้อ แต่คือทั้งสี่ด้านเขียนกลไกเดียวกันสี่ครั้งคนละชื่อ** และตอบคำถามเดียวกันไม่ตรงกัน

| รอยต่อ | อาการ | ตัดสิน |
|---|---|---|
| **`total_minor` คืออะไร** | สามชื่อ สามทิศ หนึ่งในนั้น derive ย้อนกลับจากสกุลต่างประเทศ | `grand_total_thb_minor` เป็นฐานเดียว · invoice เป็นชั้นแสดงผล · override เป็น THB เสมอ |
| **อำนาจอนุมัติ** | กฎ "สองคน" ถูกเขียนซ้ำ **6 ครั้ง** ด้วยคู่คอลัมน์ 6 คู่ ทุกคู่มีรูของตัวเอง (เช่น ผ่านเมื่อ `approved_by IS NULL`) | ตาราง `approvals` ตัวเดียว + **สองมิติ**: `margin` (ทุกอย่างที่ลดยอดที่ลูกค้าจ่าย — รวมส่วนลด FX) และ `cashflow` (ทุกอย่างที่ลดเงินที่ได้ก่อนเปิดผลิต) · ประเมิน**ที่ระดับเอกสารตอน submit** ไม่ใช่ต่อแถว |
| **เงินที่หายไปลงบัญชีอะไร** | ค่าธรรมเนียมธนาคารก้อนเดียวกันลง `settlement_variance` ขาเข้า และลง `revenue` ขาออก · `refunds.currency` มี CHECK สองตัวที่ขัดกันตรงๆ | ผังบัญชี **9 บัญชี ตั้งชื่อครั้งเดียว** — `bank_thb · remittance_in_transit · deposit_held · refund_payable · credit_clearing · trade_receivable · revenue · forfeited · settlement_variance` |
| **`scheduledDepositMinor`** | **สามสูตร** บนรูป 30/70 เดียวกันได้ ฿5,530 กับ ฿18,432 — ต่างกัน ฿12,902 และมันคือเพดานที่ตัดสินว่าลูกค้าได้คืนเท่าไร | ฟังก์ชันเดียวใน `core` · **pin ลง `orders` ตอน submit** เพราะเป็นเงื่อนไขสัญญา ไม่ใช่ค่าที่คำนวณตอนยกเลิก |
| **"งวดนี้ปิดหรือยัง"** | สามคำตอบป้อนประตูเดียว — สลิปถูกรับ (ปิด) / เงินยังไม่เข้า (ยังไม่ได้รับ) / คอลัมน์ที่อ้างถึงไม่มีอยู่จริง | แยก `settled_minor` (fold allocation ในสกุลของงวด) ออกจาก `cash_thb_minor` (fold `bank_thb`) **ห้ามเอามาแทนกัน** — ข้อ 7.6 สั่งไว้แล้วว่าตัวสะสมต้องระบุสกุล |
| **ตาราง override สองตาราง** | สองฟังก์ชันต่างอ้างว่าเป็น "จุดเดียวที่ผลิตเงินที่มีผล" | เหลือตัวเดียว · ชั้นตารางงวดรับ input แค่ `grand_total_thb_minor` |
| **`submit_for_payment` pin อะไร** | ทั้งสี่ด้านอ้างว่า pin ที่นี่ โดยไม่มีใครรู้ว่าอีกสามคน pin อะไร | ธุรกรรมเดียว pin **เจ็ดอย่าง**: `catalog_version · rate · core_version · vat_rate · forfeit_policy · payment_policy · scheduled_deposit_thb` แล้วออกเอกสารหนึ่งแถวที่ hash ครอบทั้งเจ็ด |

**ลำดับการตัดสินใจ — เขียนตารางก่อนลำดับนี้จะได้สคีมาที่ขัดกันเอง (และรอบนี้ได้มาแล้วสี่ชุด):**

```
ตอบ VAT (ตอบแล้ว — ข้อ 4.4)
  → นิยาม grand_total_thb_minor หนึ่งเดียว
    → นิยาม scheduledDepositMinor หนึ่งเดียว
      → นิยาม roundHalfUp รวมค่าติดลบ
        → จึงเขียนตารางได้
```

⚠️ **สองอย่างที่รอบนี้ทำให้แย่ลงและต้องระวัง**

1. **การอนุมัติสองคน 8 จุดในสายงานเดียว** — ข้อ 7.7 เตือนไว้เองว่าคนตรวจสลิปคือคอขวดและจุดเสี่ยงเดียว **การเพิ่มด่านอนุมัติคือวิธีที่แน่นอนที่สุดที่จะฆ่ามาตรการควบคุมตัวเดียวที่มีความหมาย** → ต้องรู้ว่าบริษัทมีคนกี่คนก่อนเขียน trigger ถ้ามีคนเดียวต้องมีโหมดผู้ใช้คนเดียวที่**ตั้งใจออกแบบ** ไม่ใช่เกิดจากการกดผ่าน
2. **ตารางนโยบายว่างเปล่าวันแรก** — ไม่มีดีไซน์ไหนบอกว่า "ไม่มีแถว" แปลว่าอะไร · fail-closed = ให้ส่วนลดไม่ได้เลยจนเจ้าของกรอกตาราง · fail-open = ฟีเจอร์เป็นของประดับ → **ต้องมีเส้นทาง smoke ที่ผ่านได้โดยไม่ต้องอนุมัติ**: ใบ THB ฿8,791 · มัดจำ 30% · สลิปใบเดียว · ยืนยัน · ผลิต · ส่ง · ปิด

**หน้าจอที่งานนี้ต้องมีแต่ยังไม่มีใครออกแบบ** — หน้าปรับใบเสนอราคา (คือสิ่งที่เจ้าของสั่งมาตรงตัว) · กล่องขาเข้าของผู้อนุมัติ · เอกสารที่มีเลขที่และ sequence (ใบเสนอราคา/ใบแจ้งหนี้/ใบกำกับภาษี/ใบลดหนี้) · ใบสั่งผลิต · หน้ากระทบยอดสเตทเมนต์

**และลูกค้าเห็นอะไรเมื่อฝ่ายขายแก้ใบที่ตกลงไปแล้ว — ตามที่ออกแบบไว้ตอนนี้คือ ไม่เห็นอะไรเลย** ไม่มี diff ไม่มีช่องทางแจ้ง ไม่มีปุ่มปฏิเสธ · ลูกค้าแสดงความไม่ยินยอมได้ทางเดียวคือไม่โอนเงิน ซึ่งทำให้ออร์เดอร์ค้างตลอดกาลเพราะไม่มี timeout **นี่คือช่องว่างที่ใหญ่ที่สุดของฟีเจอร์นี้และต้องออกแบบก่อนเฟส 5**

### 8.2 กับดัก cache ที่จะพาบั๊กเดิมกลับมา

**ISR ที่ `revalidate=3600` จะโชว์ราคาที่เก่าได้ถึงหนึ่งชั่วโมง ในขณะที่ API คิดราคาจาก Postgres สด** — นี่คือความเสี่ยงข้อ 1 ในร่างแรกเป๊ะๆ ("ราคาบนจอไม่ตรงกับใบแจ้งหนี้") ที่ถูกพากลับเข้ามาโดยการตัดสินใจเรื่อง cache

→ ต้องมี `revalidateTag('product:'+id)` ที่ dashboard เรียกตอนแก้สินค้า **บวก** `priceVersion` ที่แนบไปกับ payload และ API ปฏิเสธ order line ที่ `priceVersion` ไม่ตรง

**และ:** `searchParams` ใน `generateMetadata` ทำให้หน้ากลายเป็น dynamic โดยอัตโนมัติ — prerender ไม่ได้ ISR ไม่ได้ ต้องเลือกอย่างใดอย่างหนึ่ง

**และ:** สกุลเงินกับหน่วยวัดเป็น preference ต่อผู้ใช้ แต่ไม่ได้อยู่ใน cache key ใดเลย ทั้งที่ `ProductCard` render `formatBaht(...)` ฝั่ง server อยู่แล้ว → ต้องเลือก: ใส่ใน URL · ย้ายการ render เงินไป client island · หรือ fix หนึ่งสกุลต่อ locale

`line-height: 1.6` เลือกมาเพื่อสระไทย — เทวนาครีต้องการเยอะเช่นกัน CJK ไม่ต้อง ใช้ค่าเดียวแล้ว override ต่อ script ไม่ต้องทำ type scale 8 ชุด

### 8.5 ระบบ UI — shadcn/ui

> **ตัดสินแล้ว** ใช้ shadcn/ui เป็นฐาน UI

เหมาะกับงานนี้มาก เพราะแดชบอร์ดต้องการ `Table` · `Sidebar` · `Dialog` · `Form` · `Command` ซึ่งเป็นของที่เขียนเองแล้วได้ไม่ดีเท่า และ shadcn **คัดลอกซอร์สเข้ามาในโปรเจกต์** ไม่ใช่ dependency ที่ล็อกเราไว้

**ข่าวดี: โมเดลสีเข้ากันได้อยู่แล้ว** — shadcn v4 ใช้ `@theme inline` กับชื่อเชิงความหมาย (`bg-primary`, `text-muted-foreground`, `bg-background`) ซึ่งเป็นแนวเดียวกับ token ของโปรเจกต์เป๊ะ แค่ต้อง map ชื่อเข้าหากัน

#### 🚨 แต่ชนกับกฎที่บังคับใช้อยู่จริงในโค้ดตอนนี้

`src/index.css:14–17` ลบสเกลมาตรฐานของ Tailwind ทิ้งสี่ namespace ด้วย `: initial` เพื่อให้ token เป็นสิ่งที่**เครื่องมือบังคับ ไม่ใช่รีวิวบังคับ** — ตรวจแล้ว กฎนี้ได้ผล 100%: โค้ดปัจจุบันใช้ `text-sm` `text-xs` `text-base` `rounded-md` `font-sans` `sm:` `xl:` รวมกัน **0 ครั้ง** เทียบกับสเกลของโปรเจกต์ **193 ครั้ง**

**และ shadcn generate โค้ดที่ใช้สเกลเหล่านั้นทั้งหมด** ผลคือคอมโพเนนต์จะ**ไม่ผลิต CSS เลยสำหรับคลาสเหล่านั้น ไม่ error ไม่เตือน** — ตัวหนังสือกลับไปเป็น 16px ของเบราว์เซอร์ ดูเหมือนดีไซน์พลาด ไม่เหมือนบั๊ก

> กฎนี้ถูกสร้างมาเพื่อจับ**โค้ดที่คนเขียน** พอมาเจอ**โค้ดที่เครื่อง generate** มันเปลี่ยนจากตาข่ายนิรภัยเป็นกับดักทันที

#### สะพาน token — ลด `: initial` จากสี่ namespace เหลือหนึ่ง

| namespace | ทำอะไร | เหตุผล |
|---|---|---|
| `--text-*` | **ปลดล็อก แล้ว map 1:1 เข้าสเกลเดิม** — `xs`→12 `sm`→13 `base`→15 `lg`→18 `xl`→24 `2xl`→34 `3xl`→52 | ทั้งสองชื่อผลิต CSS ตัวเดียวกัน · คอมโพเนนต์ที่ generate มาได้สเกลของโปรเจกต์อัตโนมัติ |
| `--breakpoint-*` | **ปลดล็อก** ครบชุด แต่โค้ดที่เขียนเองยังใช้แค่ `md` `lg` | shadcn ใช้ `sm:` `xl:` เป็นครั้งคราว |
| `--font-*` | `--font-sans: var(--font-body)` | `font-sans` ต้อง resolve เป็น IBM Plex Sans Thai |
| `--color-*` | 🔒 **คง `: initial` ไว้** แล้ว map ชื่อ shadcn เข้า palette | นี่คือ namespace ที่วินัยสำคัญจริง — `bg-slate-800` ต้องพังต่อไป |

`--spacing-*` และ `--radius-*` ไม่เคยถูกลบ → `size-4` `gap-4` `rounded-md` ใช้ได้อยู่แล้ว

#### ⚠️ กับดักที่ต้องระวังตอน map สี

`--lime` มีกฎในสเปก v1 ว่า **ห้ามเกินสองจุดต่อหน้าจอ** (ราคา + ปุ่มหลักตัวเดียว) ถ้า map `--color-primary: var(--color-lime)` ตรงๆ **ปุ่ม shadcn ทุกตัวจะเป็นสีมะนาวโดยปริยาย และกฎจะถูกละเมิดตั้งแต่หน้าจอแรก**

→ `--color-primary` ต้อง map เข้าสีกลาง · การใช้มะนาวต้องเป็นการเลือกอย่างตั้งใจต่อจุด ไม่ใช่ค่า default ของคอมโพเนนต์

#### ขอบเขต

| แอป | ใช้ยังไง |
|---|---|
| `apps/dashboard` | **shadcn เต็มรูปแบบ** — โค้ดใหม่ทั้งหมด ไม่มีภาษาภาพเดิมให้รักษา ได้ประโยชน์สูงสุด |
| `apps/web` | **shadcn สำหรับของทั่วไป** (`Dialog` `Sheet` `Select` `Tabs` `Table`) · **คงของที่เขียนเองไว้สำหรับ configurator** — `ElevationDrawing` `PriceSummary` แถบล่างที่วัดความสูงด้วย `ResizeObserver` และ chip ตัวเลือกที่มีการขีดฆ่าตามกฎ ล้วนเป็นภาษาภาพเฉพาะงานที่ shadcn ไม่มีและจะสู้กัน |

**ตอนเริ่ม** `npx shadcn@latest init` ยังไม่เคยรัน (ไม่มี `components.json`) · ทำที่เฟส 0 พร้อมโครง monorepo · **อย่าติดตั้งลงต้นแบบ Vite ตอนนี้** เพราะจะถูกรื้อทิ้งอยู่ดี

## 9. รีวิวลูกค้าหลังส่งมอบ

อยู่ในโจทย์ตั้งแต่แรก แต่ร่างก่อนหน้ามีแค่ป้ายชื่อเฟส 7 ไม่มีการออกแบบ

### 9.1 รีวิวผูกกับ *บรรทัดในออร์เดอร์* ไม่ใช่กับสินค้า

ได้สามอย่างฟรีในทีเดียว: **การซื้อจริงพิสูจน์ได้เอง** (ไม่ต้องมีระบบ verified-purchase แยก) · รู้คอนฟิกที่เขาสั่งจริง (ขนาด สี กระจก) · และแสดง "รีวิวจากคนที่สั่งขนาดใกล้เคียงกัน" ได้

> รีวิว 2 ดาวที่เขียนว่า "เล็กไป" เป็นความเห็นต่อ**ขนาดที่ลูกค้าเลือกเอง** ไม่ใช่ต่อสินค้า — ถ้าผูกกับสินค้าอย่างเดียวจะอ่านคะแนนผิดตลอดไป

### 9.2 หน้าต่างเวลา — เปิดตอน `delivered` แต่คำเชิญไม่ควรมาทันที

งานอะลูมิเนียมตัดสินคุณภาพได้หลังผ่านฝนไปรอบหนึ่ง ไม่ใช่หลังติดตั้งสามวัน — รอยรั่ว บานตก อุปกรณ์ฝืด โผล่ทีหลังทั้งนั้น

→ รับรีวิวได้ตั้งแต่ `delivered` **ไม่มีวันปิด** · แต่**คำเชิญ**ส่งหลังส่งมอบ N วัน (ตัวเลขอยู่ในข้อ 13) และส่งครั้งเดียว

### 9.3 บริษัท "ซ่อน" ได้ "ลบ" ไม่ได้ และคะแนนนับเสมอ

นี่คือข้อที่ตัดสินว่าคะแนนรวมมีความหมายหรือเป็นของประดับ

- ซ่อนได้เฉพาะเมื่อผิดนโยบาย (หยาบคาย เปิดเผยข้อมูลคนอื่น ไม่เกี่ยวกับสินค้า) **ต้องบันทึกเหตุผลและคนที่กด**
- **คะแนนยังนับในค่าเฉลี่ยแม้ข้อความถูกซ่อน** — ไม่งั้นการซ่อนกลายเป็นเครื่องมือแต่งคะแนน
- ตอบกลับได้ **หนึ่งครั้งต่อรีวิว** ไม่ต้องทำเป็นเธรด

**การกลั่นกรองต้องมีเพดานเวลา** — ถ้าไม่มีใครกดภายใน N วัน **ให้ขึ้นเอง** ระบบอนุมัติก่อนเผยแพร่ที่ไม่มี SLA จะกลายเป็นระบบที่รีวิวไม่เคยขึ้นเลย ซึ่งเป็นความล้มเหลวแบบเดียวกับคิวคืนเงินในข้อ 7.12

### 9.4 รูปที่ลูกค้าแนบมา — สองกับดัก

1. 📍 **ต้องลบ EXIF โดยเฉพาะ GPS** ลูกค้าถ่ายหน้าต่างบ้านตัวเอง พิกัดบ้านติดมากับไฟล์ **การเผยแพร่รูปนั้นคือการเผยแพร่ที่อยู่ลูกค้า**
2. **ลบรูปได้โดยที่คะแนนยังอยู่** — แนวเดียวกับข้อ 7.6 ที่บอกว่าลบภาพสลิปได้แต่เก็บบัญชีแยกไว้

### 9.5 cache กับ "5.0 ★ จากรีวิวเดียว"

หน้าสินค้าถูก cache (ข้อ 8.2) รีวิวใหม่เปลี่ยนค่าเฉลี่ย → ต้อง revalidate เจาะจงสินค้านั้น ไม่ใช่ปล่อยให้ค้าง

และ **ห้ามโชว์ค่าเฉลี่ยโดยไม่โชว์จำนวน** — "5.0 ★" จากรีวิวเดียวอ่านเหมือนโฆษณา ไม่ใช่ข้อมูล

⚠️ **ระบบจะไม่มีรีวิวเลยหลายเดือน** (วันนี้มีสินค้า 81 ตัว ออร์เดอร์ 0 ใบ) → **ซ่อนส่วนรีวิวทั้งบล็อกจนกว่าจะมีจริง** อย่าโชว์ "ยังไม่มีรีวิว" 81 หน้า

## 10. การแจ้งเตือน

ไม่ได้อยู่ในโจทย์ แต่ทุกอย่างพึ่งมัน — 9 สถานะ × ทุก transition · คำเชิญรีวิว · การคืนเงิน · คิวของผู้อนุมัติ · และ**ช่องว่างที่ใหญ่ที่สุดจากรอบ "แก้ไขได้ทุกค่า": ลูกค้าไม่เห็นอะไรเลยเมื่อฝ่ายขายแก้ใบที่ตกลงไปแล้ว**

### 10.1 outbox ที่อ่านจาก `order_events` ไม่ใช่ `sendEmail()` ในโค้ด transition

`order_events` เป็น append-only อยู่แล้วตามข้อ 7.1 — **การแจ้งเตือนควรเป็นผู้บริโภคของตารางนั้น** เขียนแถว `notifications` ใน**ทรานแซกชันเดียวกับ event** แล้วให้ worker ส่ง

| ถ้าเรียกส่งตรงในโค้ด transition | ถ้าใช้ outbox |
|---|---|
| SMTP ล่ม → transition rollback (หรือแย่กว่า: สำเร็จแต่ลูกค้าไม่รู้เรื่อง) | สถานะเปลี่ยนสำเร็จเสมอ การส่งค่อยตามมา |
| retry ไม่ได้ | retry ได้ มี `dead` เป็นสถานะจริง |
| ตอบไม่ได้ว่า "ส่งอะไรไปแล้วบ้าง" | ตอบได้ — สำคัญมากตอนมีข้อพิพาท |
| เพิ่ม LINE = แก้ 20 จุด | เพิ่ม LINE = เพิ่ม adapter ตัวเดียว |

**ตัดสินตอนนี้ราคาถูก ตัดสินทีหลังแพง** — การถอด `sendEmail()` ออกจาก transition handler 20 จุดคือ refactor ที่ไม่มีใครอยากทำ

### 10.2 LINE คือช่องทางจริงในไทย แต่อีเมลคือช่องทางที่รับประกัน

ข้อ 6 ตัดสินไปแล้วว่า LINE เป็นตัวชี้ขาดเรื่อง auth — เรื่องแจ้งเตือนก็เหมือนกัน คนไทยอ่าน LINE ไม่อ่านอีเมล

**แต่** LINE OA ผลักข้อความมีค่าใช้จ่ายต่อข้อความ และลูกค้าต้องเพิ่มเพื่อนก่อน → **อีเมลเป็นช่องทางที่ต้องมีเสมอ LINE เป็น opt-in ที่ใช้ก่อนถ้ามี**

⚠️ **จุดที่ funnel เสียคน** — สเปก v1 ตั้งใจให้ดูราคาได้โดยไม่ต้องล็อกอินและไม่ต้องให้เบอร์ นั่นถูกสำหรับ*ช่วงเลือกดู* แต่**ตอนขอใบเสนอราคาต้องได้ช่องทางติดต่ออย่างน้อยหนึ่งช่อง** ไม่งั้นแจ้งอะไรไม่ได้เลยทั้งสาย — ต้องออกแบบให้ขอตรงนั้นจุดเดียว และขอให้น้อยที่สุด

### 10.3 เหตุการณ์ ผู้รับ และเหตุผล

| เหตุการณ์ | ถึงใคร | ทำไมต้องมี |
|---|---|---|
| ส่งใบเสนอราคาให้ลูกค้า | ลูกค้า | จุดเริ่มของสาย |
| 🔴 **ใบเปลี่ยนหลังลูกค้าตกลงแล้ว** | ลูกค้า | **ต้องมี diff และปุ่มคัดค้าน** — ดู 10.4 |
| ได้รับสลิป | ฝ่ายขาย | สลิปที่ไม่มีใครเห็นคือเงินที่ไม่มีใครนับ |
| ยืนยัน / ปฏิเสธสลิป | ลูกค้า | การปฏิเสธไม่ใช่ transition (ข้อ 7.3) ลูกค้าจะไม่รู้เลยถ้าไม่แจ้ง |
| เริ่มผลิต · รอติดตั้ง · ส่งมอบ | ลูกค้า | เหตุผลเดียวที่ลูกค้าจะไม่โทรมาถาม |
| คำเชิญรีวิว | ลูกค้า | ข้อ 9.2 |
| อนุมัติ / โอนคืนเงินแล้ว | ลูกค้า + คิวพนักงาน | ข้อ 7.12 — คำสัญญาที่ค้างต้องมองเห็น |
| **มีเรื่องรออนุมัติ** | ผู้อนุมัติ | รอบที่แล้วสร้างคำขออนุมัติ 8 จุดโดยไม่มีที่ให้มันไปโผล่ **วันแรกผู้จัดการจะไม่รู้ว่ามีอะไรรออยู่** |

### 10.4 ปุ่มคัดค้านของลูกค้า — ไม่ใช่ของแถม

ตอนนี้ลูกค้าไม่ยินยอมได้ทางเดียวคือ**ไม่โอนเงิน** ซึ่งทำให้ออร์เดอร์ค้าง `awaiting_payment` ตลอดกาลเพราะไม่มี timeout

→ การแจ้งว่าใบเปลี่ยนต้องมี **(1) สิ่งที่ตกลงไว้ (2) สิ่งที่เปลี่ยน (3) ปุ่มยอมรับ (4) ปุ่มคัดค้าน** และการคัดค้านต้องเป็น event จริงที่เข้าคิวฝ่ายขาย

**และต้องแสดงการเปลี่ยน *ขอบเขต* ไม่ใช่แค่การเปลี่ยน *ยอด*** — เกณฑ์ "ยอดลดลงไม่ต้องให้ลูกค้ารับใหม่" ปล่อยให้ลดจำนวนจาก 2 เหลือ 1 บานแล้วเติมค่าบริการเท่ากันได้ฟรี

### 10.5 สามอย่างที่พังเงียบถ้าไม่ทำตั้งแต่แรก

1. **ส่งซ้ำ** → idempotency key `(event_id, recipient, channel)`
2. **พายุข้อความ** — แก้ใบ 5 ครั้งใน 10 นาที ต้องไม่ส่ง 5 ฉบับ · รวบภายในกรอบเวลา ด้วยกุญแจรวบแบบเดียวกับ undo/redo ใน v1 (`src/lib/history.ts`) ที่รวบตามความหมาย ไม่ใช่ตามเวลา
3. **`dead` ที่ไม่มีใครเห็น** — ถ้าส่งไม่สำเร็จแล้วเงียบ **บริษัทจะเชื่อว่าบอกลูกค้าไปแล้ว** ต้องขึ้นคิวเหมือนคิวคืนเงิน

### 10.6 ภาษา — แจ้งเตือนใช้ค่าปัจจุบัน เอกสารใช้ค่าที่ตรึงไว้

- **การแจ้งเตือน** ใช้ภาษาที่ผู้รับตั้งไว้ ณ ตอนส่ง — เขาเปลี่ยนเป็นอังกฤษก็ควรได้อังกฤษ
- **เอกสาร** (ใบเสนอราคา ใบแจ้งหนี้ ใบกำกับภาษี) ใช้ภาษาที่**ตรึงตอน `submit_for_payment`** พร้อมของอีกเจ็ดอย่างในข้อ 7.13 — เอกสารที่พิมพ์ซ้ำแล้วได้คนละภาษาคือเอกสารที่ใช้อ้างอิงไม่ได้

เทมเพลต ~12 เหตุการณ์ × 8 ภาษา = ~96 ข้อความ **เป็นคอขวดคนแปลชุดเดียวกับข้อ 13** วางแผนพร้อมกัน

## 12. ความเสี่ยงที่ต้องจับตา

1. **ราคาบนจอไม่ตรงกับใบแจ้งหนี้** — `core` ชุดเดียว + api คิดราคาเองเสมอ + `priceVersion`/`documentHash` ที่ทำให้ mismatch เป็น 409 ไม่ใช่การคิดเงินเงียบๆ
2. **ซ่อนเมนูแทนการตรวจสิทธิ์** — enforce ที่ api ทุก endpoint + boot-time route audit
3. **ข้อมูลที่ค้างอยู่ถูกตีความผิดตอนเปลี่ยนหน่วย** — bump storage version ใน commit เดียวกันเสมอ
4. **ปัดเศษผิดสกุล** — VND/LAK ไม่มีทศนิยม แยก `minorExponent` ออกจาก `roundToMinor`
5. **ยอดรายบรรทัดไม่บวกได้ยอดรวม** — ปัดสองชั้นตามลำดับในข้อ 4.3(ข) แล้วบวกจากบรรทัดที่ปัดแล้ว
6. **อัตราแลกเปลี่ยนค้างเก่า** — อัตราตรึงแปลว่าไม่มีอะไรเตือนเมื่อค่าเงินขยับ ต้องมีรายงานว่าอัตราไหนตั้งไว้นานแล้ว
7. **อาร์บิทราจเมื่ออัตราแบกส่วนต่างตลาด** — พอไม่ใช่ FX บริสุทธิ์ สกุลเงินต้องผูกกับปลายทางจัดส่ง
8. **สลับหน่วยแล้วขนาดเปลี่ยน** — canonical immutable, สลับหน่วยคือการแสดงผลล้วน
9. **งานแปลเนื้อหา 81 × 8** — วางแผนคนและเวลา
10. **สลิปปลอม** — การตรวจด้วยคนคือมาตรการควบคุมเดียว หน้าจอต้องทำให้ความไม่ตรงเห็นได้ทันที
11. **ยอดที่ต้องจ่ายเปลี่ยนขณะสลิปรอตรวจ** — `awaiting_payment` แก้ไขได้ ต้อง recompute งวดและตีสลิปเป็น superseded
12. **สิทธิ์ตรวจแค่ประเภทผู้กระทำ** — `actors: ['customer']` ไม่ได้แปลว่าลูกค้าคนนี้ ความเป็นเจ้าของต้องอยู่ใน query
13. **สถานะเปลี่ยนระหว่าง submit กับ accept** — pin catalog version และอัตราตอน submit ไม่ใช่ตอนสร้างสัญญา
14. **เงินก้อนเดียวถูกนับสองที่** — ยกเงินไป order ฉบับแก้ไขต้องเป็น allocation ที่ชี้กลับต้นทาง ไม่ใช่แถวงวดใบใหม่ (ข้อ 7.8)
15. **ริบเงินเกินภาระที่ตกลงกันไว้** — เพดานผูกกับภาระมัดจำ ไม่ใช่กับเงินสดที่บังเอิญรับมา
16. **`fault` มาจาก request body** — ลูกค้าประกาศเองว่าบริษัทผิดแล้วได้เงินคืนเต็ม
17. **อนุมัติคืนเงินแล้วยอด/ปลายทางยังแก้ได้** — ต้องมี trigger แช่แข็ง ไม่ใช่วินัยของทีม
18. **VAT เป็นป้ายกำกับ ไม่ใช่การคำนวณ** — ทุก % ที่คิดจากยอดรวมจะผิดจนกว่าจะแก้ (ข้อ 7.5 จ)

**ข้อที่มติรอบ "แก้ไขได้ทุกค่า" ทำให้แย่ลง — ต้องแก้ทะเบียน ไม่ใช่แค่เพิ่มบรรทัด**

| ข้อ | เปลี่ยนไปยังไง |
|---|---|
| **1** ราคาบนจอ ≠ ใบแจ้งหนี้ | มาตรการเดิม ("api คิดเองเสมอ + 409") **ใช้ไม่ได้แล้ว** เปลี่ยนเป็นการตรวจที่มา (ข้อ 7.9 จ) · และพื้นผิวราคาเพิ่มจาก 1 เป็น 6: คำนวณสดในเบราว์เซอร์ · computed baseline · effective · สกุลนำเสนอ · เอกสารที่แช่แข็ง · **ลิงก์แชร์** (`shareLink.ts` ให้เบราว์เซอร์ปลายทางคำนวณราคาสดเอง ไม่มี order id — ไม่มีใครบอกว่ามันแสดงอะไรหลังใบนั้นมี override) |
| **5** บรรทัดไม่บวกได้ยอดรวม | เพิ่มพร้อมกัน: แถว adjustment · แถว balancing · ค่าบริการ · บรรทัดอิสระ · การถอด VAT · การแปลงสกุลต่อบรรทัด — บนเอกสารที่ต้อง foot **สองสกุล** |
| **10** สลิปปลอม / คนตรวจคือมาตรการเดียว | **แย่ลงหนักที่สุด** — เพิ่มด่านอนุมัติสองคน 8 จุดในสายงานเดียว (ข้อ 7.13) |
| **11** ยอดเปลี่ยนขณะสลิปรอตรวจ | เดิมมีทางแก้ยอดทางเดียว ตอนนี้มีห้าทาง และมีหน้าต่างเวลาใหม่ที่ยังไม่มีชื่อ: **สลิปยืนยันแล้ว งวดปิดแล้ว แต่เงินยังไม่เข้าบัญชี จึงยังอยู่ `awaiting_payment` ซึ่งเป็นสถานะที่แก้ราคาได้** |
| **3** ข้อมูลค้างถูกตีความผิด | `priceSnapshot` เปลี่ยนรูปร่าง · `aluform.quote.v1` ยังไม่มี `schemaVersion` (ยืนยันแล้ว) · **ต้อง bump ใน commit เดียวกัน** |
| **15** ริบเกินภาระ | เพดานกลายเป็นค่าที่**ฝ่ายขายกำหนดเองและแก้ซ้ำได้** ตามมติข้อ 1+4 → ต้อง pin ตอน submit (ข้อ 7.13) |

19. **ไม่มีโครงสร้างพื้นฐานทดสอบชั้น DB** — รอบนี้ประกาศ CHECK ~30 ตัวและ trigger ~15 ตัว แต่เทสต์ 219 ตัวใน 13 ไฟล์**เป็นเทสต์ฟังก์ชัน pure ทั้งหมด ไม่มี DB สักตัว** ทุกประโยค "กันความล้มเหลว" ยังพิสูจน์ไม่ได้ว่ายิงจริง → ต้องมี pgTAP หรือ testcontainers ก่อนเฟส 5
20. **PDPA ขัดกับ append-only ตรงๆ** — เลขบัญชีเป็นทั้งข้อมูลส่วนบุคคลที่ต้องลบได้ และเป็นหลักฐานชิ้นเดียวที่พิสูจน์ว่าคืนเงินถูกคน · ยังไม่มีตารางระยะเก็บรักษา ไม่มีเส้นทาง DSAR
21. **แจ้งเตือนล้มเหลวเงียบ** — ถ้า `dead` ไม่ขึ้นคิว **บริษัทจะเชื่อว่าบอกลูกค้าไปแล้ว** ทั้งที่ไม่เคยส่งถึง (ข้อ 10.5)
22. **พิกัด GPS ติดมากับรูปรีวิว** — ลูกค้าถ่ายหน้าต่างบ้านตัวเอง การเผยแพร่รูปคือการเผยแพร่ที่อยู่ ต้องลบ EXIF ก่อนเสมอ (ข้อ 9.4)
23. **ซ่อนรีวิวกลายเป็นเครื่องมือแต่งคะแนน** — คะแนนต้องนับในค่าเฉลี่ยแม้ข้อความถูกซ่อน และการซ่อนต้องบันทึกเหตุผลกับคนที่กด (ข้อ 9.3)

## 13. ตัวเลขธุรกิจที่ระบบเดาไม่ได้

รอบออกแบบ "แก้ไขได้ทุกค่า" ผลิตตัวเลขที่ **agent ประดิษฐ์ขึ้นเองกว่า 30 ค่า** — เพดานส่วนลด สเปรด ค่าความคลาดเคลื่อน จำนวนวัน ทั้งหมดเป็น placeholder ที่ดูเหมือนคำตอบ หน้านี้มีไว้เพื่อไม่ให้ placeholder หลุดลง production

**กฎของหน้านี้: ทุกแถวต้องมีคอลัมน์ขวาสุด** — "วันที่ยังไม่มีคำตอบ ระบบทำอะไร" ตารางนโยบายที่ว่างเปล่าโดยไม่มีพฤติกรรมที่นิยามไว้ คือฟีเจอร์ที่ตายเงียบในวันแรก

| กลุ่ม | ต้องได้จากเจ้าของกิจการ | ค่าตั้งต้นจนกว่าจะตอบ |
|---|---|---|
| **VAT** | ~~รวมหรือไม่รวม~~ **ตอบแล้ว (ข้อ 4.4)** · ที่ยังเหลือ: ลูกค้าต่างประเทศเข้าเกณฑ์ 0% ไหม · ค่าขนส่ง/ติดตั้งเสียภาษีไหม | อัตรา **700 bp** · ทุกบรรทัดและทุกค่าบริการ `is_vat_applicable = true` · ประเภท `standard` — เปลี่ยนได้ภายหลังโดยไม่ต้อง migrate เพราะเป็นการตั้งค่า ไม่ใช่โครงสร้าง |
| **อำนาจ** | เพดานส่วนลดต่อ role (มิติ `margin`) และเพดานการลดเงินก่อนผลิต (มิติ `cashflow`) · มีผู้อนุมัติสำรองไหม | **fail-closed** — ยังไม่มีแถว = ยังลดราคาไม่ได้ · เส้นทาง smoke ต้องผ่านได้โดยไม่ต้องอนุมัติ |
| **มัดจำ** | พื้นขั้นต่ำของงวดที่ถือประตู · จำนวนงวดสูงสุด · ใครอนุมัติตารางที่ไม่มีประตูเลย (= การให้เครดิต) และมีวงเงินต่อลูกค้าไหม | ประตูขั้นต่ำ = **เต็มจำนวน** (ปลอดภัยที่สุด) จนกว่าจะตั้งค่า |
| **การริบ** | bps ต่อ (สถานะที่ยกเลิกได้ × ฝ่ายที่ผิด) — ต้องครบทุกช่อง | **ริบ 0 ทุกช่อง** = คืนเต็มเสมอ · ปลอดภัยกับลูกค้า แต่ต้องรู้ตัวว่ากำลัง ship แบบนี้ |
| **สกุลต่างประเทศ** | มีบัญชีรับสกุลต่างประเทศจริงไหม · สเปรดจริงต่อสกุล (ต้องวัดจากใบโอนจริง 5–10 ใบ **ก่อน**ตั้งค่า) · ค่าความคลาดเคลื่อนที่ยอมรับได้ · อายุใบเสนอราคาสกุลต่างประเทศ · ค่าธรรมเนียมเป็น OUR/SHA/BEN | **ปิดสายต่างประเทศทั้งเส้น** ออกใบเป็นบาทพร้อมป้าย "ราคาโดยประมาณ" ตามข้อ 4.2 เดิม |
| **การคืนเงิน** | SLA กี่วัน · ค่าธรรมเนียมโอนใครรับ · อนุญาตให้คืนเข้าบัญชีคนละชื่อไหม · ใครกินส่วนต่าง FX | SLA = **ไม่มี** (แต่คิวต้องมองเห็น) · ค่าธรรมเนียมบริษัทรับ · คนละชื่อ = ห้าม |
| **จำนวนคน** | **บริษัทมีคนตรวจสลิป/อนุมัติกี่คนจริงๆ** | ⚠️ ตอบก่อนเขียน trigger ไม่ใช่หลัง — ถ้ามีคนเดียว กฎสองคน 8 จุดจะกลายเป็นพิธีกรรมที่ทุกคนกดผ่านโดยไม่อ่าน ซึ่งแย่กว่าไม่มีกฎ |
| **รีวิว** | ส่งคำเชิญหลังส่งมอบกี่วัน · กลั่นกรองเสร็จภายในกี่วันก่อนขึ้นเอง | คำเชิญ **30 วัน** (งานอะลูมิเนียมต้องผ่านฝนก่อน — ข้อ 9.2) · กลั่นกรอง **3 วัน แล้วขึ้นเอง** ไม่ใช่ค้างตลอดกาล |
| **แจ้งเตือน** | ใช้ LINE OA ไหม (มีค่าใช้จ่ายต่อข้อความ) · กรอบเวลารวบข้อความ · retry กี่ครั้งก่อน `dead` | อีเมลอย่างเดียว · รวบ **10 นาที** · retry **5 ครั้ง** แบบถอยหลังทวีคูณ |
| **การเก็บรักษา** | เก็บเอกสาร/สลิป/เลขบัญชี/รูปรีวิวนานแค่ไหน (บัญชี vs PDPA) | 5 ปีตามเอกสารทางบัญชี — **ต้องยืนยันกับผู้ทำบัญชี** |
| **เนื้อหา** | ใครเขียนคำแปล 8 ภาษา × 81 สินค้า (คำถามข้อ 10) | คอขวดที่ไม่ใช่โค้ด |

**นอกจากตัวเลข ยังมีช่องว่างข้อมูลที่ค้างมาตั้งแต่ v1 และยังไม่มีใครเติม:**

- `pricePerSqm` เป็นตัวเลขสมมติใน **78 จาก 81 สินค้า** (หัวไฟล์ `products.ts` เตือนไว้แล้ว)
- `productSpecs` มีค่า `null` สามช่อง — ความหนาโปรไฟล์ · มาตรฐานที่ผ่าน · การรับประกัน
- จำนวนบานและทิศทางเปิดในรูป elevation อนุมานจากชื่อสินค้า
- `hardMin`/`hardMax` เชิงกายภาพต่อ CustomGroup **ยังไม่มีอยู่จริงในโค้ด** (ตรวจแล้ว `grep` ได้ 0 แถว) — จนกว่าจะได้ขอบเขตจากโรงงาน จะแยก "ข้อจำกัดของแคตตาล็อก" ออกจาก "ผลิตไม่ได้จริง" ไม่ได้ ซึ่งแปลว่า **ฝ่ายขายที่ override ข้อจำกัดจะไม่มีทางรู้ว่ากำลังข้ามอันไหน**
